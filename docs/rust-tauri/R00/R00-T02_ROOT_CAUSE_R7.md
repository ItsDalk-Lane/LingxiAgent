# R00-T02 第七轮失败后的独立根因分析

**结论：R7-F01 是 R00-A03 的真实阻断，问题在同一控件按状态分流后的效果归属；170 条动作、313 条变体全标 `CORRECT` 没有证明这些分流完整。** 分析依据为 `codex/rust-tauri-migration` 的 HEAD `16aeb380d58d68ff1a38bb46f5cc5d18f985f084`、R7 冻结候选、支持审查记录、生成器和现役源码。本文件只分析根因与下一轮修复/复审门槛；不改候选、产品、测试、任务书或总账，不提交、推送，也不把静态核对当成迁移运行验收。

## 二、为什么前六轮与全量 UI 审阅没有拦住

前几轮解决的问题确有进展：R1—R4 逐步补入口、HTTP 效果和逐叶场景；R5 将自动化面板从仅有读取叶扩为增删改查/启停，并引入动作矩阵；R6 补最终消费者范围并发现空草稿、新增错误 toast 等结果误写；R7 修复这些点名文字并复核 26 页。遗漏发生在这些成果之间的粒度：**页面级目标集合包含 update，动作 `#03` 的目标集合却只有 toggle；同一控件的启用/停用分支没有各自成为必须检查的变体。** 此前的点名检查集中在新增空草稿、启用空提示词拒绝和失败文字，能够证实这些结果，却不自动证明提示词非空时启用走哪个请求、是否合并未保存草稿。R6 根因报告要求“生产触发/消费者→动作变体→真实效果叶/场景”的双向差集，R7 的记录未将 `job.enabled` 两侧分别列为源头事实和候选键，因而没有真正完成这一层差集。

现行门禁的边界可以从代码直接说明。`r00_t02_source_gates.py:186-228` 检查动作 ID、非空文字、行号、F-ID/场景一致、调用链与目标叶**有文件交点**、已有 `control_variants` 与目标集合一致、页面支持目标与动作目标并集一致。它没有从 `AutomationCard.toggleEnabled()` 的两条分支独立推出“应有的两条动作→效果边”；`control_variants` 是可选的，当前 `#03` 正好没有变体，仍可通过。`AutomationPanel.tsx` 和 `server/routes/desk.ts` 各承载多个 action，共用文件交点也不足以区分 `action:'update'` 与 `action:'toggle'`。`r00_t02_inventory.py:1434-1453` 随后以矩阵为输入生成 `FEATURE_INVENTORY.json` 和 `FEATURE_STAGE_ACCEPTANCE.json` 的相同动作与断言；三份一致性是复制无漂移，不是与真实分支一致。源码 SHA 冻结和负例能查出源码变化、错误 ID 或删掉已有支持边，不能查出**现役源码没有变化、候选从一开始少写一条状态分流**。

支持审查 `R00-T02_UI_ORACLE_REVIEW.json` 的修复后部分报告 170/170 动作、313/313 显式变体 `CORRECT`，但 `#03` 的 `observed_from_source` 已提到“update/toggle”，`target_feature_ids` 仍只列 toggle；它的证据锚在卡片 `:119` 的状态判断、面板 `:99` 的徽标更新和通用路由 `:331,:1062`，没有列卡片 `:127`、`action:'update'` 及两个具体服务端 `case`。`#03` 在 313 条显式变体里没有一条记录，故“313/313”只审了**候选已经声明的变体**。`source_checked:true`、`acceptance_embedded:true` 和全量 `CORRECT` 是已有记录的状态，不能使缺席的启用变体出现。更早基线的 `#03` 也挂 toggle，修复后审查沿同一动作身份关闭旧文字问题，未把其已观察到的双路径反向加入目标集合。这是可见证据支持的流程缺口；不推测个别审阅者的主观原因。

因此本轮与 R5/R6 的共因仍是“候选自选集合的内部一致性被当作生产行为的完整性”：先有页面支持边，再从既有动作求并集；先有动作变体，再逐个标正确；先有动作文字，再生成场景；先有页面摘要，再冻结文件。即使每层 SHA 和计数都正确，缺席的**条件分支→服务端效果叶→本页适用场景**不会进入任何差集。页面汇总旧文案则显示另一面：已有字段之间尚未做语义/内容一致性核对。不能靠继续增加总行数或只改 `#03` 一句“启用走 update”消除这个共因。

## 三、最小而完整的修复边界

1. **先修本页事实。** 从卡片点击的 `job.enabled` 两侧建立独立可检查变体，必要时将 `#03` 拆成启用/停用两个动作；启用接 `cron.update` 的 F-ID/场景，停用接 `cron.toggle`。启用的正例至少覆盖“无其他草稿变更仍发 `enabled:true`”和“已有未保存标题、周期、提示词、模型草稿随同一次 update 保存”；空提示词 Agent 启用在卡片被拒绝。停用走 toggle，不能被写成 update。分别记录请求/服务端拒绝后的状态及现役 UI 反馈，不把新增按钮的错误 toast 复制过来。`#05` 保留独立保存的“有变更才请求”语义。两叶既有行为身份无需仅为这次 UI 错挂另造 F-ID；真正需要补的是动作到现有叶、叶场景和本页结果场景的适用关系。
2. **同步所有消费位置。** 更新矩阵的动作、显式变体、`call_chain`、`target_feature_ids`、`target_scenario_ids`、本页成功/空态/失败文字及 `page.error_empty_paths`；据此重新生成 `FEATURE_INVENTORY.json`、`FEATURE_STAGE_ACCEPTANCE.json` 的动作回写和本页断言。支持审查记录须重新从源码作结论，`#03` 启用和停用各给 UI 状态条件、回调、请求的 `body.action`、服务端 `case`、目标 F-ID/场景和结果证据。不能只把旧 `CORRECT` 或旧 SHA 搬到新候选。页面汇总可以保留，但同一 action ID 的空态/失败态须与动作字段一致；若它仅用于展示，应明确由动作派生，避免双份人工真相。
3. **补一条独立于候选的发现与比较门禁。** 对每个可见控件/自动加载，从 JSX 事件及状态条件出发，沿 props 回调、hook/store、请求/IPC 到具体 `body.action` 或本地最终效果，形成“控件＋前置状态/输入条件＋效果终点”集合；同一按钮若条件不同且落入不同效果叶，应产生两条边。静态无法解析的动态调用列出调用点、可能终点和 `MANUAL` 裁决，不当作已经覆盖。将这个**由现役源码得到的集合**与矩阵动作/变体及本页场景双向比较：生产边缺归属、候选边无生产依据、结果/场景只适用于另一状态，均非零。文件交点、页面目标并集、SHA 和文字非空继续作为结构/漂移门禁，但不再承担语义证明。所有 26 页在这一粒度复审；无需因此重开已独立通过的 HTTP、A04 分类和迁移实现范围。
