# 灵犀任务清单改版执行计划书

日期：2026-09-11  
状态：计划已编写，功能尚未实施。  
本轮授权：编写执行计划；不包含功能修改、提交、推送、打包安装或发布。

## 一、要达到的结果

用户在聊天时，不打开右上角的运行信息，也能知道灵犀准备做什么、正在做什么、还剩多少工作。

采用 DeepSeek Harness 的输入框上方清单布局，保留灵犀未完成任务跨轮次延续的能力。完成后给用户一个可回看的结果，取消剩余工作时不把它误记成完成。

本计划的成功标准是：进度容易看到，状态含义准确，重新打开会话后结果一致。模型把任务标记为完成，只代表它记录了完成状态，不能代替实际工作验证。

## 二、现状与参考依据

以下是本次查到的现状，不是待实施功能：

| 项目 | 当前行为 | 改版要解决的问题 |
| --- | --- | --- |
| 入口 | 清单位于右上角运行信息内，默认收起；外层数量不包含清单进度 | 用户很难随时看到进展 |
| 状态 | 待开始、进行中、已完成 | 无法准确表达受阻或取消 |
| 完成 | 全部完成后从当前清单区域消失 | 缺少明确的收尾反馈 |
| 延续 | 未完成清单按会话保留，可从历史恢复 | 这是优势，需要保留 |
| 用户操作 | 只有全部标记完成；会修改历史并通知模型 | 想关闭清单时，可能误把没做的事记为完成 |
| 更新方式 | 模型每次提交完整清单；多个进行中只产生警告 | 并行工作的约定不清晰 |
| 恢复保护 | 已有会话隔离、当前分支恢复、防旧历史覆盖实时更新 | 改版不能破坏这些机制 |

另有一项待验证疑点：实时处理任务工具结果时，失败或缺少清单内容的结果可能被转换为空清单，而历史恢复会跳过坏记录。实施时必须先用回归测试确认，再按结果修正；本计划不把它当作已经证实的故障。

- [清单规则](https://github.com/deepseek-ai/deepseek-harness/blob/c291e7961a515f6d7af9304e7fd1d257929aef26/packages/todo/tool-todo/src/index.ts)：完整替换、内容校验、并行规则、下一轮清空展示。
- [消息中的清单摘要](https://github.com/deepseek-ai/deepseek-harness/blob/c291e7961a515f6d7af9304e7fd1d257929aef26/packages/client/ui-tool/src/client/tool/toolviews/todo-row.tsx)：更新清单时显示完成数量和当前步骤。

灵犀此次不采用“新一轮开始就清空未完成清单”的规则。

## 三、本次范围

### 必须完成

1. 在主聊天输入框上方显示清单进度条，移除右上角运行信息中的重复清单。
2. 展开后查看完整清单；显示当前进度和受阻原因。
3. 未完成清单跨轮次保留；已结束清单保留收尾摘要，并按明确规则收纳。
4. 区分收起清单、确认全部完成、取消剩余任务。
5. 支持多个真实并行步骤同时显示进行中。
6. 保证实时更新、历史恢复、会话切换和旧记录兼容。
7. 完成对应测试、类型检查、界面构建和实际界面验收。

### 本次不扩展

不加入截止日期、提醒、优先级、拖拽排序、用户逐项编辑、任务依赖或跨代理共享清单；不把清单改造成项目管理系统。不增加自动执行任务、自动重试或阻止回复结束的机制。

主桌面聊天和复用同一聊天页面的移动布局纳入验收；独立快捷聊天窗口、其他通信平台保持现有入口，核对共享数据变化不会造成异常。

## 四、确定的展示与交互规则

### 4.1 清单进度条

- 放在主聊天输入框上方，与输入框内容宽度对齐，随输入区固定显示，不随消息长列表滚走。
- 没有清单时完全不占位置。
- 默认收起；标题整行可点击，键盘 Enter 或空格也可切换。
- 左侧固定清单图标，标题为“任务”；沿用此前对固定图标的偏好，不使用悬停时替换图标的箭头。
- 标题按状态显示非零数量，例如“2 已完成 · 1 进行中 · 3 待开始”。存在受阻项时必须保留“受阻”提示。
- 收起时可显示首个进行中步骤；多个步骤同时进行时补充“另有 2 项进行中”，不只显示其中一个而隐藏并行事实。
- 用户已经展开后，流式更新和模型更新清单不得自动把它收起。
- 展开偏好按会话在本次应用运行期间保存；切换到其他会话不沿用上一会话的展开状态。不要求跨应用重启记住展开偏好。

### 4.2 展开的清单

| 状态 | 展示规则 | 是否算完成 |
| --- | --- | --- |
| 待开始 | 灰色空心状态图标和任务描述 | 否 |
| 进行中 | 强调色状态图标；有进行中描述时显示该描述 | 否 |
| 受阻 | 明确的受阻图标、任务描述和原因 | 否 |
| 已完成 | 完成图标，文字适当减弱 | 是 |
| 已取消 | 取消图标，明确写出已取消 | 否 |

保留清单自身的完成状态图标；此前移除的是工具调用消息行尾的成功勾号，两者含义不同。

- 长任务描述在展开后可以换行，不依赖鼠标悬停才能阅读；收起摘要使用省略号。
- 清单较长时，内部滚动区域最高约 240px，同时不超过可用窗口高度的 30%，不能挤掉输入和发送操作。
- 标题约 13px，类型图标约 14px，采用项目现有深浅主题颜色；状态不能只靠颜色区分。
- 输入框上方若已有待发送消息、权限提示等内容，保留原有相对顺序；清单作为独立区域接入，不覆盖提示或发送按钮。
- 清单工具在消息流中显示“任务 · 已完成 2/6 · 正在检查兼容性”一类短摘要；沿用现有统一消息行及当次调用详情，不再铺一份常驻完整清单。

### 4.3 用户操作

| 操作 | 实际含义 | 是否修改任务状态 |
| --- | --- | --- |
| 点击标题收起 | 只隐藏展开的条目 | 否 |
| 确认剩余任务已完成 | 用户明确认定剩余工作已经做完；未完成项改为已完成，已取消项保持取消 | 是，并记录用户操作 |
| 取消剩余任务 | 待开始、进行中、受阻项改为已取消；已完成项保持完成 | 是，并记录用户操作 |
| 收纳已结束清单 | 隐藏已结束的摘要，历史仍可查看 | 只改变当前展示，不改完成或取消结果 |

改变任务状态的操作放在展开清单的次级操作区。模型正在输出时禁用完成和取消操作，服务端同样拒绝；收起仍可使用。

“取消剩余任务”只改变这份计划，不等同于终止终端进程、工作流或其他后台任务。界面在操作旁用简短说明表达这一点。历史中区分模型更新与用户收尾，并向后续模型上下文提供准确说明。

## 五、清单在不同时间的处理规则

| 场景 | 必须发生的行为 |
| --- | --- |
| 模型首次建立清单 | 显示进度条，默认收起 |
| 更新部分任务状态 | 原位置更新，保留用户展开状态 |
| 回复结束但还有未完成任务 | 保留清单，不自动补成已完成 |
| 停止输出或发生运行错误 | 保留最后有效清单；不让旧的进行中图标继续表现为仍在执行，提示“本轮已停止，仍有未完成任务” |
| 用户补充要求或说“继续” | 未完成清单继续保留，等待模型明确更新 |
| 所有任务都完成 | 显示“全部完成 · 6 项”，保留到下一条用户请求被服务端正式接受，或用户主动收纳 |
| 部分完成、其余取消 | 显示“已结束 · 4 已完成 · 2 已取消”，不得显示全部完成 |
| 已结束后开始新一轮 | 收纳旧摘要；旧记录保留在历史中；若发送失败或请求未被接受，不提前收纳 |
| 主动收纳后重新打开会话 | 不重新弹出已收纳摘要 |
| 切换会话或切换历史分支 | 从目标会话、目标分支恢复，不串用其他会话的清单 |
| 工具更新失败或数据损坏 | 显示更新失败，保留最后一份有效清单，不当作清空 |
| 明确提交空清单 | 作为明确清空处理，与失败结果严格区分 |

不通过关键词猜测“这条消息是不是一个新任务”。未完成清单一直保留到模型明确替换、明确清空或用户取消。模型说明要求保留仍属当前工作的未完成事项，但本次不增加逐项身份与删除审计系统。

## 六、数据和模型规则

### 6.1 数据原则

- 延续每次提交完整清单的方式，不引入逐项修改接口。
- 保留普通描述和进行中描述，兼容旧消息；新增受阻、取消状态和必要的原因说明。
- “任务完成情况”和“清单是否收纳”分开记录。已经收纳不代表完成，已经结束也不代表全部成功。
- 沿用会话历史作为真实记录，不另建一份与历史分离的清单数据库。
- 每次有效变更关联当前会话、分支和清单版本；用户操作针对其看见的那一版清单。后台已更新时，旧操作应提示刷新，不能把新任务一起完成或取消。
- 实时与历史使用同一套状态校验和恢复规则。坏数据明确报错或跳过坏快照并提示，不转换成成功或空清单。
- 保留当前按会话隔离、防较旧历史请求覆盖实时更新的保护。

### 6.2 旧记录与接口兼容

- 旧的三态记录原样恢复，缺少新字段时采用明确的兼容规则，不推断取消或受阻。
- 旧版曾明确移除的清单、旧的手动全部完成记录，不因升级重新弹出。
- 对未带新版本标识的旧全完成记录，沿用过去已收纳的语义；新格式的完成清单才采用“保留收尾摘要”的行为。
- 旧接口入口如仍有调用方，保留入口并转入统一处理；新界面必须传递清单版本。不能安全匹配的旧请求明确提示更新或刷新，不偷偷作用于另一份清单。
- 服务端与界面应配套升级；遇到不支持的新状态明确标注兼容问题，不映射成完成。核查共享类型的其他消费者，防止未知状态导致异常。
- 历史记录不做批量重写，不删除用户已有记录。

### 6.3 模型使用规则

- 简单一步的工作不强制创建清单；复杂工作先列出可执行步骤。
- 每次发送完整清单，任务内容去除首尾空白，空白条目和重复条目明确拒绝。
- 多项进行中是合法情况，前提是工作实际并行；本次直接支持，不新增用户配置开关。
- 单项做完及时更新，不等全部结束才一次打勾。
- 无法继续时标记受阻并说明缺少什么；用户取消的事项不能自动恢复为进行中，除非后续请求明确重新开展。
- 回复结束前检查清单与实际结果是否一致；这是模型使用约定，不是验证系统。不能通过强制循环、自动补全状态制造“全部完成”。
- 子代理清单仍归子代理会话，主代理自己的清单由主代理维护；本次不自动把子代理条目合并进主清单。

## 七、实施顺序与阶段交付

| 阶段 | 具体工作 | 交付与通过条件 |
| --- | --- | --- |
| 1. 固定行为和补回归 | 核对当前分支、已有改动和消费入口；用测试复现失败更新、完成即消失、历史恢复等行为；建立旧消息样本 | 可以证明要改的行为，明确哪些是现状、哪些是缺陷 |
| 2. 统一状态与记录 | 定义状态、原因、收纳标记和版本；实现共享校验；接入工具结果、用户操作、实时事件与历史恢复 | 成功、失败、清空可区分；重开会话结果一致；旧记录不复活、不串会话 |
| 3. 完成界面迁移 | 实现输入框上方清单；移除胶囊中的重复入口；加入计数、展开、并行摘要及收尾操作；适配主题和窄窗口 | 新入口可完整使用，发送、权限提示及消息滚动不受影响 |
| 4. 打通模型和生命周期 | 更新工具说明及消息摘要；接入服务端正式接受新请求后的收纳规则；处理停止、继续、全部完成和取消 | 未完成不因新一轮消失；已结束摘要按规则收纳；无虚假完成 |
| 5. 集成验收与交付 | 跑受影响检查；在实际界面操作完整流程；同步功能说明与必要的生命周期文档；清理本次临时验收材料 | 验收表逐项有结果，明确未覆盖环境；交付可审阅改动 |

阶段 2 的数据约定确定后，界面与服务端工作可以独立并行。整合由同一负责人完成，先确认实时和历史一致，再进行最终界面验收。各阶段不需要重复确认普通实现细节。
