- PaddleOCR 官方确认 PaddleOCR-VL-0.9B 与 Apache-2.0 项目；GLM-OCR 官方确认 0.9B、模型 MIT、代码 Apache-2.0，但官方自托管主路径是 Python/vLLM/SGLang，另列 Ollama/MLX 专门路径。当前尚无“无需 Python 的三平台原生 q4 sidecar”官方闭环证据。
- Qwen3-ASR-1.7B 官方模型存在；当前官方检索尚未证明任务指定的 GGUF/llama.cpp 或 `qwen3-asr-rs` 三平台分发闭环。
- IndexTTS 2.5 官方项目存在，但当前官方材料仍以 Python 工程为主；`q4` 原生 sidecar、Windows/macOS Intel 分发和用户给定性能阈值尚未被证明。
- 结论：核心调度、资产、接口和 fake-runtime 合同可以真实实现；具体模型条目只有在运行时、资产、许可证和平台产物均有证据时才能标为 ready，不能以 manifest 占位冒充八模型完成。
- 2026-09-02 再核官方资料：`sherpa-onnx-node` 明确提供 Windows x64、macOS arm64/x64、Linux x64/arm64 预编译 Node 包且无需 Python；官方 Node API 覆盖 SenseVoice 与 Kokoro，因此这两项 small 通道具备直接实现依据。

## 现有调用链核对

- 现有媒体运行时契约的 `local-cli` 只是“一次命令一次执行”的结构化包装：基于 `execFile`、固定超时和输出解析，尚无长驻进程、健康检查、取消信号、日志轮转、崩溃看门狗或确定性进程树回收。它可复用参数契约思想，不能直接当完整 sidecar 管理器。
- 现有语音识别内置适配器均是远程请求；本地适配器尚不存在。语音服务已经在调用前建立观测、用量归属和音频大小桶，适合让本地适配器复用同一上层边界。
- `system-speech` 当前只是无凭据 Provider 声明，注释说只有运行时适配器存在时才可选；实际注册表尚未注册该协议对应的本地实现。
- 知识嵌入目前统一从核心引擎进入操作模型解析和嵌入客户端；记忆嵌入也复用同一操作模型体系。本地路由应加在共享执行边界，不能在知识和记忆各造一套。
- 文档抽取返回值目前只含文本、格式和警告；扫描版 PDF 有明确失败分类。图片输入、逐页光栅化和本地文字识别尚未接通。
- 项目已经有统一出站代理配置和基于 `undici` 的按地址代理分发；所有模型 manifest/资产下载必须显式复用这层。`core/media/download.ts` 只是生成图片落盘工具，不是通用下载器。
- 设置页已有网络代理、媒体能力默认项和模型可观测区；服务端路由通过统一组合根挂载，并有路由安全白名单。新增本地模型路由必须同步该安全登记，不能只加处理器。
- 当前模型能力代码和五语言文案已经出现“语音合成”概念，但尚未看到对称的合成服务；实现前要区分“模型元数据能力”与“真实执行链”。
- 本地模型若新增服务端路由，除组合根外还必须同步 `server/http/route-security.ts` 与合同测试；新增运行时代码要核对 `export-manifest.json`、CLI 闭包和开放边界。
- 新持久状态（manifest 缓存、下载进度、模型登记、日志）不能随意落盘：项目有统一持久化登记、访问点扫描和 schema 指纹门禁。即便不用数据库，也需声明所有者、路径、恢复/清理和允许写入点。
- 新原生模块或平台 sidecar 会改变 Electron 壳表面：`build/shell-surface-manifest.json` 与 `package.json` 的 asar/extraResources 是双向合同；分发改动必须两边同步并接受对应测试。
- 重新从当前提交搜索确认：仓库没有 `packages/local-models`、`lib/local-models` 或任何已接线本地模型实现；当前 Phase 2 必须从源码建立，不能依赖已丢失外部补丁。
- `lib/net/outbound-proxy.ts` 已提供 npm `undici` 的逐 URL dispatcher；manifest 和资产下载必须显式使用同一份 `undici` fetch + `fetchDispatcherForUrl()`，不能使用 Node 内建 fetch 假定会继承代理。
- 语音识别服务已经把 adapter 调用包在统一 trace、用量归属与语义来源记录中；本地 adapter 应作为注入运行时的无网络 adapter 注册，避免在 adapter 内再建第二套观测账本。
- `extractDocument()` 当前只接受 buffer/path 并在扫描 PDF 失败时返回 `scanned-pdf`；OCR 接线需要通过可选依赖注入保持普通文档原行为，不能让底层抽取模块反向持有完整 Engine。
- 仓库现有 `lib/extract-zip.ts` 已拒绝 symlink 和路径穿越，但仍会把每个 entry 完整读进 Buffer 后写盘；它适合当前小型插件/技能包，不适合多 GB 模型资产。为避免回归公共安装链，本地模型需使用独立的流式、限额、CRC 和 manifest-entry 校验器。
- 再次逐行对照原需求 4.1–4.4：manifest 刷新必须带 ETag/缓存并在离线或解析失败时回退；运行时目录固定在 `${LINGXI_HOME}/runtime/local-inference/...`；`model.json` 明确要求版本、总字节数与 `sha256Manifest`。首版注册表只在内存计算后两项，现已改为磁盘字段必填并交叉校验，避免重启扫描与即时导入得出不同身份。
- 组合根复核修正了先前判断：`full-root.ts` 只承载头像、卡片、桌面、日记等闭源产品面；本地模型子系统位于开放 `lib/`，不依赖闭源内容，应像语音识别与知识路由一样注册到 `open-root.ts`，这样完整产品和开放服务入口得到同一能力。权限仍必须显式 local-owner 登记。
- 四条业务链首轮复核：知识和记忆都在 Engine 的同一嵌入执行边界汇合，因此本地嵌入应在这里按稳定 `local:` 身份分流，而不是分别改两套存储；现有语音识别上层已经负责会话文件、状态、观测和用量，本地 STT 只需成为无凭据适配通道；文档抽取已有依赖注入口，扫描 PDF 的 `scanned-pdf` 分类是接 OCR 的最小边界。
- 生命周期顺序存在一个接线约束：Engine 构造时已经创建知识与语音服务，而 LocalModelsSubsystem 目前在服务端代理初始化后才创建并挂到 Engine。业务适配必须用延迟 getter 或显式 attach，不能在 Engine 构造期假设本地子系统已经存在。
- 当前仓库只有完整的语音转写服务，没有对称的语音合成执行服务；TTS 不能仅在模型元数据里打标签，需要新增一条复用会话文件和观测边界的最小服务/路由，再由桌面朗读入口调用。
- 回读权威业务要求确认：本地 STT 的固定协议名是 `local-offline-asr`，应在既有语音适配器注册表中注册且禁止网络请求；OCR 必须保留普通文档原路径，只在图片或扫描 PDF 时调用，并在成功结果 warnings 留 `ocr:<modelId>`；TTS 需要对称新服务和适配器，Bridge 失败只能显式降级文本，不能丢消息。
- 原始要求中的真实三平台模型下载、原生运行时和性能阈值依赖尚不存在的经验证资产。代码合同、管理面、假运行时集成和本机打包可继续实现；F2/F3/F9–F12 中依赖真实资产的部分以及全部硬件矩阵必须保持 `NOT_EXECUTED`，不能由 mock 测试替代。
- 桌面“本地模型”区已挂到现有模型设置页，现有 UI 测试统一 mock `lingxiFetch`；若不为 `/api/local-models` 返回完整状态，组件会正确显示错误但无法覆盖真实行为，因此需新增独立组件测试并把父页默认 mock 补成有效空状态。
- 原始任务对设置页的要求不止目录展示：下载需有暂停/恢复/取消、速率与剩余时间，手动导入需含打开目录/拖入、后端探测结果需可见，删除还需说明向量缓存保留。当前首版只完成分组、安装/删除、基础配置和单条进度，后续不能把它标成完整 UI 验收。
- 助手消息的完成操作统一由消息页脚动作数组生成，已经包含复制、截图、反馈和选择；朗读应作为同级动作注入，并从同一消息的纯文本块提取内容。现有页脚在流式阶段整体隐藏，所以“完成后朗读/暂停/停止”可在这一边界实现，而“随回复逐句合成”需要另接实时文本增量，不能混为已完成。
- 桌面主界面已有带鉴权的请求封装和全局 toast；本地合成路由返回带格式、采样率和 base64 音频的成功体。浏览器端可用 Blob/Object URL + Audio 播放，停止时必须暂停、归零并回收 Object URL，组件卸载也要中止请求和释放资源。
- Bridge 的飞书与 QQ 入站已经把语音归一为 `audio` 附件并下载成内存文件；微信当前只采用平台自带的语音文字，明确不保留语音附件。统一附件解析目前只给提示“收到语音”并把音频放进入站文件，不会调用语音识别服务。
- Bridge 的语音转写不能复用只接受会话文件 id 且限定 `voice-input` 展示类型的桌面后台方法；应复用更底层、已经带统一观测/凭据/本地分流的直接音频入口，给 Bridge 下载的受限临时文件做转写，并把文字在送入会话前加入用户可见提示。微信若平台没有下发原始音频，只能保留平台文字，不能伪造本地离线转写。
- 更窄且更安全的复用点已找到：Bridge 会话在调用模型前会把所有入站音频写入受管的会话文件缓存、登记文件 id，并拿到真实会话路径；现有直接转写入口正好接受这三个身份且不限于桌面 `voice-input`。因此无需创建系统临时目录，也无需让平台适配器接触语音服务。
- Bridge 会话管理器由 Engine 依赖注入，新增“读取语音配置 + 调用已登记文件转写”两个窄闭包即可。只有显式启用并配置默认语音模型时执行；成功把带标签的转写追加到本轮用户输入，失败追加不含底层错误的明确提示，原语音附件仍保留。
- Bridge 出站媒体统一服务目前只接已登记文件、远端地址和受控本地路径，不接受裸内存；但多数平台适配器已经声明是否支持内存上传、音频类型和大小上限。对本地合成结果可在 Bridge 管理器做一条受能力声明约束的内存发送，QQ 这类明确拒绝裸内存的平台保持文本，不落临时文件绕过归属边界。
- 语音回复必须是显式 opt-in，适合放在本地 TTS 配置中，默认关闭。现有 Bridge 可能已流式发送文字，因此最安全语义是“文字始终送达，能力允许时再附加本地语音”；合成或上传失败只记脱敏诊断，已送达文字就是明确降级，不能为了纯语音形态冒险吞掉正文。
- 实际的嵌入模型选择器并不使用供应商详情页的统一展示列表，而是知识笔记本与记忆设置共同读取 `/api/preferences/models` 的 `operation_models`。供应商页当前只统一聊天、图像、视频和语音识别，把 embedding 硬塞成 chat 会破坏类别语义。
- 因此本地 embedding 的真实接线点应是服务端模型偏好响应：把“已经安装且完整性通过”的 embedding 注册表条目投影成 `{provider:'local', id:'local:...@...@...', operations:['embedding']}`，两个现有选择器会自动出现同一项并按稳定身份保存；未安装或被删除后不再作为新选项，但原配置仍由 UI 的不可用项语义保留。
- `/api/preferences/models` 当前直接返回供应商注册表的 operation catalog；Engine 的通用操作解析器要求远端地址和凭据，但本地嵌入执行已在知识/记忆入口按 `provider=local + local:` 身份提前分流。因此本地目录项只应作为选择/持久化投影，不应伪造地址、协议或凭据去骗过通用远端解析器。

### Phase 7 初步根因核对
