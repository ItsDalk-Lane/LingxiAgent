## 当前职责与修复

真实桌面入口已经是 `desktop/src/react/services/ws-message-handler.ts`，旧 app-ws-shim 文档名不是另一条生产消费链。新增 `StreamAdmission` 在真实分发水位层和真实 buffer 入口共同使用，归入主端严格检查范围；不是仅测试使用的抽象。

- 已退役 stream 的 start/delta/end/tool/status 不能切回当前身份。Run 身份独立比较，不以 runId=streamId 推断。Run 结束的旧强制“身份不匹配也终结当前run”分支移除。
- 身份接纳先于 pending、知识检索指示、队列终结与其他 store 副作用。重复序号不会重复投影；真实帧存在缺口时不提前写入，而是经原 `resume_stream` 路由补取。
- 迟到的旧 stream_resume 响应不能清空新流。历史重建清除水位时保留身份屏障，并发重建共享屏障。
- 纯旧协议尚未见明确 stream 身份时兼容；已经进入明确流的无身份聊天帧不会被贴成当前流。会话级 compaction 保留自身语义。知识卡的宿主本地生成入口显式调用 handleLocal，不以远端无身份兼容路径绕行。
- 退役身份各至多 256 条。容量满后不淘汰并重新接纳旧身份，而是经现有 WS 请求权威全量快照。流身份集合饱和后，后续换流继续要求权威快照；快照恢复重建会清 Run 局部记录但保留流屏障。`260 runs` TCP 测试证明不会第257轮卡死，首轮旧 start 在恢复后仍拒绝。此策略在极长会话下可能增加重建次数，不宣称性能改善。

服务端本来就给每条 emitStreamEvent 附 streamId/seq；同一助手 Run 内多个模型轮次通常复用同一 stream，插话可在同一 stream 下切换 runId。会话级 trace 归组没有改动，并复跑同会话多轮 trace 复用套件。

## 真实GUI发现的审批状态复活（追加修复）

真实工具审批完成后，后续输出曾使输入区重新显示待批准。独立WS原始记录确认 confirmation_resolved 已正常广播（全局事件无 streamId），它不满足新增接纳门禁条件，故不是缺少streamId被误拒。真实 route → WebSocket → consumer → manager 回归进一步复现：store 投影被改为 confirmed，但 manager 原始块仍 pending，下次增量覆盖回旧状态。

最小修复只让现有 StreamBufferManager 的 session_confirmation 块同步 confirmed/rejected/timeout，并沿原 publishBoundary 投影；原 resolved 分支接线，不新增状态层，不执行或重试工具。新增回归覆盖 pending → resolved → 后续模型输出 → settled，断言快照及终态不复活 pending。

`confirmation-projection-red` 退出1；完整原审查HEAD临时源码快照的同一反例 `confirmation-projection-original-head` 也退出1，证实该问题原本存在，但属于本轮实际消费者投影验收范围，已一并修复。`confirmation-projection-green` 退出0；`confirmation-f03-regression` 19文件276测试通过；`confirmation-renderer-typecheck` 实际renderer strict与`confirmation-strict`核心严格检查均退出0。上述日志均在F03证据目录。最终生产变更仅新增上述两处接线，已通知打包代理重新构建。
