# 交付与验收模板

以下模板是执行时填入真实结果的结构，不是现在已经完成的报告。空数组/空字段表示尚未执行；不能原样提交后声称完成。

## 1. 阶段报告最小结构

```markdown
# PXX 阶段执行报告

## 结论
PASS / FAIL / BLOCKED；说明通过或阻塞的明确原因。

## 实际输入
START_SHA、END_SHA、分支、锁文件摘要、OS/arch/Node/npm、未提交修改保护。

## 任务逐项结果
任务ID｜实际实现或UNCHANGED_VERIFIED｜生产入口与源码位置｜测试与日志｜旧路径去向｜状态。

## 场景逐项结果
场景ID｜具体测试文件和用例名｜fixture摘要｜实际操作｜预期/实际｜命令ID｜证据｜状态。

## 接线和旧路径
新链真实消费者、旧入口退出/兼容理由、有无双写和隐式回退。

## 验证
每条命令的exit code和日志；首次失败/重跑都记录；未运行与环境受阻单列。

## 数据、权限与平台
数据版本/备份/恢复，主体与资源边界；实际验证平台和产物摘要。

## 差异与限制
批准的行为差异、未完成项、现有非关键问题、范围外建议。

## 回退与下一阶段
逐步回退条件和动作；保护新增数据；交接的接口/测试/旧兼容约束。
```

## 2. 结构化结果起始模板

文件建议：`P00_RESULT.json`（其他阶段改ID）。下列状态均未开始。

```json
{
  "schema_version": 1,
  "stage_id": "P00",
  "status": "NOT_STARTED",
  "research_sha": "8037fae7a6f621549f5b7db4c4d0bba3862ddc07",
  "start_sha": null,
  "end_sha": null,
  "environment": {
    "node": null,
    "npm": null,
    "os": null,
    "arch": null,
    "lockfile_sha256": null
  },
  "tasks": [],
  "acceptance_cases": [],
  "commands": [],
  "baseline_failures": [],
  "scope_deviations": [],
  "legacy_paths": [],
  "blocked_items": [],
  "next_stage_handoff": null,
  "implementation_performed": false,
  "project_tests_executed": false
}
```

填充规则：task条目至少有id、implementation_action、source_locations、consumer_locations、test_ids、legacy_action、status、evidence。implementation_action限定MODIFIED/REMOVED/UNCHANGED_VERIFIED/BLOCKED，不从是否有diff自动判断是否完成。

case条目至少有id、test_path、test_name、fixture_sha256、production_entry、expected、actual、command_ids、status、evidence。PASS没有命令/手工产物证据无效。NOT_APPLICABLE必须有不可达/不适用证明；凭证/平台缺失只能BLOCKED。

## 3. 命令日志记录

每次命令保存一条JSONL索引，字段：command_id、stage_id、cwd、source_sha、argv、started_at、finished_at、exit_code、status、stdout_path、stderr_path、log_sha256、reason、retry_of。时间是实际执行时间；未运行不得填exit_code=0，应用null和BLOCKED原因。

`argv`不得包含明文token/密码；环境只记录非敏感配置。测试原始payload存受控位置，公共日志存脱敏摘要。进程超时必须记录是发送了取消还是确认退出。

## 4. 调用点与数据契约表

调用点表字段：入口ID、真实文件/符号、入口身份来源、目标业务服务、策略/权限入口、实际执行点、状态写入者、持久化点、结果消费者、当前测试、主责阶段、状态。

数据表字段：数据种类、当前版本、reader/writer、原始/派生、敏感性、备份方法、兼容旧版本、迁移必要性、激活条件、回退条件、验证命令。不要把派生索引与原始历史都当“可以清空重建”。

## 5. 旧路径退出表

字段：旧文件/符号、原职责、现真实消费者、新去向、处置（删除/仅读兼容/协议适配/仍待迁）、必要保留理由、权限影响、测试、退出条件。

保留兼容不等于允许双重业务裁决。删除也不等于自动通过；仍支持的旧数据/客户端必须继续可用。

## 6. 验收证据检查规则

检查ID唯一、引用文件存在、日志exit code与状态一致、source SHA一致、FAIL重跑链完整、fixture摘要一致、关键场景没有N/A无理由、命令未执行却没有PASS。证明实际生产入口不能只扫描到函数名；需调用链或运行记录。

关键PASS必须同时有实现/接线/行为三类证据。源码扫描与mock单元都不能独立证明产物安全。P00允许记录非阻塞旧失败但必须明确它通过的是基线工作；P08全部必需门禁必须真的通过。

## 7. 证据包和摘要

可公开打包：报告、精确补丁/提交范围、合成fixture、脱敏原始测试日志、测试结果JSON、必要截图和本地测试产物索引。禁止打包node_modules、私人资料、密钥、真实用户数据库、未许可第三方材料。

MANIFEST.sha256逐文件记录包内相对路径与真实SHA256，**不包含自身**（避免自引用摘要悖论）。生成manifest后打包，再记录ZIP文件摘要；后者不能写回同一ZIP的内部摘要清单。

## 8. 前置交接内容

NEXT_STAGE_HANDOFF.md必须包括：已验收SHA、接口和语义表、实际改动位置、已执行测试路径、必保留兼容/观察分组、未验证环境、当前数据版本、下一阶段唯一允许修改范围。不得只写“前一阶段已完成，继续”。
