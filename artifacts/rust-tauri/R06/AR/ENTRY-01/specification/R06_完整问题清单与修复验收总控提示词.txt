## R06-AR-F01｜新 Run 没有加载当前会话分支的历史上下文

严重度：HIGH。原Task：R06-T01, R06-T02, R06-T03, R06-T04。证据类型：SOURCE_CONFIRMED。本轮审查未做运行复现。

### 已确认的问题与影响

正式 execute 路由仅将 request.input 传给 ExecuteSubmission；SessionStore 随后把该输入交给 drive_run。drive_run 虽写入用户消息并编译 system prompt，却以 Vec::new() 初始化 exchange。发送时 prior=exchange.clone()，这份 exchange 只包含本 Run 后续产生的交换，并未从当前分支加载之前的用户回合、助手回复与工具交换。数据库历史读取和 fork 的存在，不能补上这条模型请求链。

同一会话下一次提问、重启后续问、fork 后第一次提问以及 rewind 后再问，都可能不携带应继承的历史。只测一个 Run 内多次模型调用，或只测试历史接口能返回数据，无法发现这个缺口。

### 必须修复的内容

1. 建立统一的运行上下文历史读取入口，按认证主体、Agent、Session 和有效 branch head 读取权威历史；先明确当前用户输入何时落库，防止重复加入。
2. 历史必须保留协议所需的角色、工具请求/结果配对、宿主和供应商调用身份、不透明签名及来源绑定。不得只把 UI 导出的最终正文当作完整模型历史。
3. fork/retry/rewind 必须选择正确的有效分支；旧分支、未确认副作用和其它会话不得混入。跨供应商不能重放不兼容 opaque 状态。
4. 将上下文压缩版本、摘要和保留后缀接入同一恢复路径；保留原始权威记录。重启后的历史加载只读，不得重新执行模型或工具。
5. 同时检查 foreground/background/child 的实际调用链；需要继承父上下文的子代理只能继承授权裁剪后的材料。

## R06-AR-F02｜rewind/retry 直接按检查点路径写文件，缺少当前授权与原子防冲突边界

严重度：CRITICAL_PATH_RISK。原Task：R06-T03, R06-T05。证据类型：SOURCE_CONFIRMED_RISK; exploit requires runtime verification。本轮审查未做运行复现。

### 已确认的问题与影响

restore_checkpoint_files 读取检查点记录的 file_path，std::fs::read 后按哈希决定 Restore，再 std::fs::write 同一路径并复读。函数只接收 storage/session/checkpoint，不接收当前 ResourceAccess 授权；写入不是临时文件＋安全替换，且读、判断、写之间没有文件身份锁定。读写会跟随可变符号链接。现有注释宣称 failed 不覆盖现状，但 std::fs::write 失败前可能已截断或部分写入。

检查点创建后撤权、路径或祖先被换成符号链接、检查与写入之间发生外部编辑，都存在越界覆盖或覆盖用户新内容的风险。哈希曾出现过不等于当前仍有权限，也不证明这一次修改来自应用。此处未在本次审查环境实际执行破坏性反例。

### 必须修复的内容

1. 使 rewind/retry 的文件恢复经共享 ResourceAccess 与当前授权，逐文件重验规范化目标、符号链接/重解析点、授权撤销和主体范围；不得只信创建检查点时的授权。
2. 采用平台适用的安全打开、文件身份/版本比较、同目录临时写入与原子替换方案；将读到写之间的竞态纳入契约，不依赖裸字符串路径或一次哈希检查。
3. 在持久化检查点前完整验证可恢复内容与来源；恢复时区分已达目标、确证可恢复、外部冲突、未能确认与失败。不要把“任意旧检查点见过同一字节”当作外部编辑不存在的充分证据。
4. 写入失败、磁盘满、取消和服务崩溃要保留原文件或如实报告可能部分发生的副作用，不能声称 failed 就等于零写入。
5. 复核所有会写回文件的 restore/rewind/retry/filehistory 路径，复用同一安全原语，避免仅修一个 HTTP 入口。

### 5.2 工作单元与顺序

每个F-ID对应一个一次性修复Task `R06-AR-Wxx`，例如W02修F02。推荐顺序：

`W02 → W03 → W12 → W01 → W05 → W06 → W07 → W08 → W09 → W10 → W11 → W13 → W04 → W15 → W14 → FINAL-R06`

先止住文件/数据风险，再补上下文和知识链，最后收口映射和全门禁。依实际接口可在有证据的依赖图上调整顺序，不能少做、合并成一个长期Agent或只完成前几个问题。需要某前置时先处理前置，不让两个写代理同时改同一源码、锁文件或数据库。

一项修复涉及另一F-ID的公共代码时，登记影响和重跑义务；不能因为“那是另一个Task”留下同根因旁路。后续Task修改公共契约，先前结果按影响标STALE并复跑。最终Stage审查重新核验全部集成。

### 5.3 固定循环

`NEW EXECUTOR → 逐项自检 → 对抗性自检 → NEW INDEPENDENT REVIEWER → PASS则精确交付；FAIL则NEW REPAIR → NEW REVIEWER`

审查者发现的所有同根因问题应一次汇总。连续两轮同族失败时，创建全新的ROOT-CAUSE代理做全路径分析，形成完整修复矩阵再派新Repair。不得设“达到三轮自动算通过”，也不得为追求永远完美无限增加与任务无关需求。

BLOCKED与FAIL分开。实现难、测试失败、发现新代码缺陷不是跳过理由。缺真实凭证、目标OS或授权且当前关卡确需它，才记精确BLOCKED；已获原规格允许的延期保留owner/截止而不改成PASS。

## 9. 逐项结果格式与自动检查

每个F-ID至少登记：`original_requirement/source_path/observed_fact/reproduction_status/root_cause/all_affected_paths/repair_commits/self_check/adversarial_self_check/independent_review/remaining_scope/status`。

每项必须经历三层，不能省略任何一层：

| 检查层 | 谁执行 | 必须做什么 | 不能替代为 |
|---|---|---|---|
| 逐项自检 | 本Task执行/修复代理 | 核对所有修复条目与C-ID、原Steps/A-ID，实际运行正常和错误路径 | 一句“测试已通过” |
| 对抗性自检 | 同一执行/修复代理 | 主动制造越界、竞态、异常、空筛选或旧根因变异，证明保护能失败关闭 | 只再跑同一正例 |
| 独立对抗性审查 | 全新空历史Reviewer | 独立读源码、亲跑C-ID、补自己的反例并核对范围/证据 | 实现者切换角色自签PASS |

本包JSON是规格，初始NOT_RUN。另建工程结果，不将规格一键改绿。JSON严格拒绝重复键，ID唯一、需求/任务/测试/证据双向映射不缺失。条件未适用须写原授权依据，不得用于豁免本文件的60个离线基础检查。

每次后续改动影响已PASS项时标STALE并重跑；不能让历史绿灯永久有效。source-only audit不等于亲跑。一个正确的失败负对照通过，是指测试准确断言了预期拒绝，不是程序实际失败却写测试PASS。

## 12. 候选冻结、提交、推送与证据体积

每个Task独立PASS后，总控核对实际源码/测试/配置与Reviewer候选一致，运行diff检查，精确暂存本Task相关文件/必要证据。不能无脑git add -A，不能混入初始用户修改、.vscode、node_modules、target或临时个人数据。

提交信息例如：`fix(rust-tauri): R06-AR-F08 preserve tool-result cap on warnings`。沿用户授权推送`codex/rust-tauri-migration`并回读远端确认。无强推、无squash旧历史。网络/权限/远端冲突不能通过强制覆盖解决。

提交成功但push失败标COMMITTED_NOT_PUSHED，不进入下一项正式DONE。仅回执/证据索引收口不改变运行行为；产品/测试语义/配置改变使相关审查过期，需全新复核。

保存足以复现的原始输入、运行命令、必要日志与摘要，不复制整套源码/.git/构建缓存到每轮证据树。当前运行自己的输出目录可通过已有安全规则排除出绑定输入，不能扩大全仓忽略规则掩盖源码变化。避免自引用hash和“把文档自身未来commit写进文档”的死循环；用独立交付回执关联最终提交与被测候选。
