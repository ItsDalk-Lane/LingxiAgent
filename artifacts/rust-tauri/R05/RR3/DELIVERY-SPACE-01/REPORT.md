# RR3 Git 交付空间只读预估

结论：**可继续小型、只读的最终分类与容量准备；当前不应据此开始完整暂存、提交或推送。完整交付空间安全尚未获证。** 旧清单中可测部分确实远小于原始 572 MB，但保守操作预算约 125–155 MB；测量结束可用仅约 246.7 MB，之后只余约 92–122 MB，且尚未计入新材料、当前文档、最终清点及同盘活动。G02 曾在 `df` 仍显示约 116 MiB 时连小文件也写入失败，因此不能把这点账面余量当可用保证。

本报告是容量准备，不是最终暂存名单、安全审查、实际 Git 交付或产品验收。R05 仍 NOT_ACCEPTED，R06_READY=false；完整默认负测、full R02/E5 及 FINAL 因空间未完成。本轮未构建、未执行历史 driver、未改仓库/Git/系统、未清理、未派子代理。只在本外置目录写小型报告与复查脚本，完成后停止写入。

## 输入与测量方法

全文读取本轮 BRIEF、RR1/RR2 MASTER、RR3 BRIEF/HANDOFF、DELIVERY-PREP-02 REPORT/REFRESH_RULES、G-REVIEW-02 REVIEW、STORAGE-03 REPORT，并补读 E 的文件所有权 brief。E03 正在写现行材料，本轮主动跳过旧 include 中全部 42 个 current document，包括 E 当前文档及协调文档，不冻结、不判断这些变化是否为源漂移。另跳过两个旧快照已变化的脚本；这是旧清点需要刷新，不是宣称出现未授权变化。

`estimate.py` 只读旧 include 与 merged-paths，在大小/mtime 仍相等的文件上逐块计算内容 SHA256、`blob <字节数>\0 + 内容` 的 Git SHA1/SHA256，以及 zlib level 1/6 长度；压缩结果只过内存，不保存压缩副本、不写 Git 对象。再以当前实际属性运行无 `-w` 的 `git hash-object --stdin-paths` 核对 Git 真正的内容转换，按实际 SHA1 用 `git cat-file --batch-check` 批量确认已有对象。没有创建新 index/tree/commit；目录/index仅为容量模型。

8,982 个重复路径不需要重复储存 blob。已存在对象的“压缩量”是本轮同内容重算模型，不是把现有 packed delta 大小当 loose 大小，也不等于当前需要再写这些对象。缺失内容若 level 6 压缩为 63,192,076 bytes，但当前默认 loose 是 level 1，预算采用 68,969,094。最大新增原内容 18,232,835 bytes，最大 level 1 对象约 12,207,397 bytes。

文件系统 `f_frsize=4096`；`f_bsize=1048576` 是建议 I/O 块，不作为每个小对象分配 1 MiB。4 KiB 向上取整是数据块预算，不含 APFS 元数据、空间保留、快照或并发活动；不承诺等于真实消耗。缺失对象覆盖全部 256 个前缀目录，而这些目录已经全部存在，**不是每对象再创建一个目录**。目录当前 `st_blocks=0` 不代表追加目录项和元数据不占空间，另留少量余量。

## index、tree、提交及推送开销

- 现有 index 6,139,139 bytes，版本 2，共 38,066 entries。只将本轮可测路径加入容量模型后为 51,840 entries，基础 v2 大小约 8,294,432 bytes；不含最终新材料和扩展区。旧 index 已占当前磁盘，不能再把它全量加到“新增”中；写新 `index.lock` 时新旧同时存在，暂存后再提交还可能再次重写。计划为索引增长、锁文件及扩展区留约 9–18 MB，后续最终名单改变时重算。
- 极保守地把容量模型的全部 7,109 个目录都当需新增 tree（实际会复用很多），未压缩 tree 约 3,033,070 bytes；用 zlib `compressBound` 的内容无关上界并逐对象 4 KiB 取整，约 **29,585,408 bytes**。模型中的零占位子树 OID 所得压缩值不是上界，报告不使用它作保证。
- commit、引用锁、reflog 和提交签名通常很小，但仍需空间。本机启用提交签名，未访问钥匙或验证可签名；默认 hooks 目录无有效 hook，未设置自定义 hooksPath/clean filter。另为目录/元数据/临时写入留小额余量，并容纳最多一个大 loose 临时对象的保守瞬时量；不把每个对象无依据翻倍。
- 综合已测旧范围，**125–155 MB 是建议计划预算，不是成功下限或严格峰值证明**；已含上述偏保守 tree/index/临时余量。当前 246.7 MB 减去预算后约余 92–122 MB，新材料尚未包含，因此不能称安全。

只读查询未发现 `core.compression`、`core.looseCompression`、`pack.compression`、`gc.*`、`maintenance.*`、`pack.*`、`http.postBuffer` 的覆盖配置。已有 2,049 个 loose 对象、19 packs（约 3.695 GB pack/idx 统计量）；加 4,207 个 blob 已接近默认 gc.auto=6700，加 tree 可能触发自动维护。`git count-objects` 还提示一个既存 88 KiB 临时对象；本轮只记录，不删除也不把它当可释放量。

建议后续获准执行 Git 交付时在具体命令使用临时 `-c gc.auto=0`，避免低空间下自动重打包；本轮未执行该写操作，也未改任何配置。该参数只约束相关自动 gc 启发式，不能阻止独立计划任务、其他 app 的 Git 写入或系统换页。

本机 Git 随附帮助依据：`git-config.1` 3594–3604 定义未覆盖时 loose level 1；8845–8849 定义 pack 默认 zlib level -1（通常 6）；5978–6004 明确 gc.auto=0 同时关闭 loose 与 pack-count 自动启发式。`git-pack-objects.1` 44–64 明确 `--stdout` 将 pack 流送标准输出；`git-config.1` 7271–7275 明确 smart HTTP 超过默认 1 MiB POST buffer 使用 chunked 以避免本地完整大 pack。origin 当前是标准 HTTPS GitHub 地址。

因此**不能再凭空加一份或两份整个 push pack 的本地磁盘量**。若远端仍具有当前基线，已测唯一 blob 的无 delta level 6 总量约 69.15 MB，可作为新内容传输量级参照；真实 pack 受远端已有对象、delta、复用对象、tree及新增材料影响，本轮未生成 pack、未联网更新远端事实，不报精确值。通常推送流可直接传出，但不能承诺零临时磁盘：签名/凭证助手、进程内存引发的系统换页、环境差异和其他进程仍未知。服务端收包空间也不由本地估算保证。

## 163 份原证的换行边界

当前 `.gitattributes` 为 `text=auto eol=lf`。只读 Git 实际计算表明，**163 路径**的原始字节与普通 Git 转换后的 blob 不同：原量 18,703 bytes，转换后 17,908 bytes。逐项都满足 `filtered = raw.replace(CRLF, LF)`，且 filtered SHA1 与 Git 实测相等。它们多为边界负测的短输出/夹具，不能将普通 `git add` 表述为保留原始字节。

`normalization-boundary.json` 给出全部准确路径、原始/转换后内容 SHA256、Git blob SHA1/SHA256、字节数及压缩长度，不含正文。115 个唯一原始 blob 当前均未存在；即使把这些 raw blob 额外加在 filtered 估算之上，4 KiB 数据块保守追加上界仅 **471,040 bytes**，不改变本次空间结论。

这是**实际交付必须保留原字节的待处理接口**。后续新分类者/独立审查者可验证逐路径 `--no-filters` 生成对象并精确更新 index 的方案，真正暂存后还须对实际 index blob 逐项核对原始 SHA/字节；本轮不实施、不批准该方案，不改 `.gitattributes`、系统配置或原证，不声称普通暂存已原样保存。
