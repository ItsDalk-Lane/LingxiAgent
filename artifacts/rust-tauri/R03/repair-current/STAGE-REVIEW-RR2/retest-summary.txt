## B4 自写独立复测 srv2_independent_retest（retest-src/srv2_independent_retest.rs，3 用例）

与执行者套件和 R1 审查者复测**均不同源**：自有 ID（req-9x / iso-7 / req-fresh-9z）、自有空白变体
（旧格式冲突用 CRLF 形态 `"request:\r\nreq-9x\r\n"`，区别于 R1 的 Tab 形态）、新增「重启后全新 ID
仍正常受理」过度阻断控制臂。夹具形态与两前辈一致：真实 composition root
（ServiceState::bootstrap_with_deps + prepare_layout 合成数据根）+ 真实 SQLite RunDatabase +
真实 supervisor/gate/dedup；替身仅脚本化 Provider 与文件外部计数器；"重启" = storage().close()
+ drop + 同数据根重新 boot。错误变体用运行时 Debug 串匹配，使同一文件可在基线 c96f7cc6 编译运行。

- (a) `srv2_a_padded_id_raw_and_canonical_retries_bind_the_one_logical_request`：
  前台真实受理 " req-9x " → 计数 +1、completed、runs=1 → 重启 → 原样 " req-9x " 与 canonical
  "req-9x" 重试均 `RequestIdBoundToEarlierRun` 且指向**同一** run、回显 canonical
  （`request_id: "req-9x"`）、runs 仍 1、计数仍 1、锚点=`request:req-9x`；
  随后全新 ID "req-fresh-9z" 正常受理并 completed（计数 2、runs 2）——非无条件拒绝。
- (b) `srv2_b_colliding_legacy_rows_refuse_as_explicit_ambiguity_never_a_pick`：
  两条旧格式 cause_id（`"request: req-9x "`、`"request:\r\nreq-9x\r\n"`）归一冲突 →
  "req-9x"/" req-9x "/"\r\nreq-9x\r\n" 三种形态重试均为 `RequestIdBoundAmbiguous`
  列出**两个** run、非单选 `RequestIdBoundToEarlierRun`、计数 0、runs=2、两条冻结行逐字不变。
- (c) `srv2_c_same_logical_id_never_crosses_session_or_principal_namespaces`：
  同一逻辑 ID " iso-7 " 在 owner×sess_local_alpha、owner×sess_local_beta、device 主体×sess_local_alpha
  三命名空间各自独立受理（计数 3、各自 run）→ 重启 → 三种重试拼写（原样/ canonical / Tab 包裹）
  各自 `RequestIdBoundToEarlierRun` 指名**自己**的 run、绝不含他命名空间 run；计数仍 3。
