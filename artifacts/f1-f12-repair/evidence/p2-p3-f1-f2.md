# P2 + P3 证据：F1 输入所有权/显式结果 + F2 会话串行与回合终结

日期：2026-09-07。范围：任务书 P2（S01–S15）与 P3（Q01–Q16），同一 coordinator 闭环。

## F2 根因（源码核实）

`ws-message-handler.ts` 的保守清理块对「任何后续会话事件」调用 `endTurnPending`，
包括 `session_user_message`——而那只是客户端自己发出消息的接收回执，不代表
助手开始响应。ack→run_start 之间的窗口期 turnPending 已被清除，队列续发可以
在回合未真正开始时提前点火。修复：保守清理排除 `session_user_message`（知识
检索标记仍由 ack 清除），turnPending 只被真正的运行事件终结。

## 架构（按任务书 P3.2，两道互相独立的门禁）

1. **传输租约**（新模块 `services/composer-send-coordinator.ts`，模块级，
   不随 InputArea 卸载丢失）：`preparing → awaiting_ack`，服务端回执
   （`noteComposerServerAck`，ws-message-handler 的 session_user_message 分支）
   释放；断连（`noteComposerConnectionClosed`，websocket.ts onclose）把
   awaiting_ack 清扫为 `delivery_unknown('connection_closed')`；回执看门狗
   15000ms 超时转 `delivery_unknown('ack_timeout')`。永不自动重发。
2. **运行忙门禁**（既有流式状态）：streamingSessions/turnPendingSessions，
   以 streamId/turnId 身份匹配（removeStreamingSession/identitiesMatch）。

`composer-send.ts` 拆为 prepare/commit 两段：

- `prepareComposerSend`：模型快照、预检（ws OPEN → 模型可用 → 视频数量/格式/
  模型能力 → 音频读取 → 视频读取）、base64 读取、载荷拼装；每个分支返回显式
  结果。图片「提示后退化为文件引用」策略原样保留（#1647）。
- `commitPreparedComposerSend`：同步复核（revalidate）→ onCommit 清理钩子 →
  appendOptimisticUserMessage → ws.send，全部在同一个同步窗口内，无 await。
- `dispatchComposerSend` = 薄组合，返回判别联合 `ComposerDispatchResult`。
  transport_submitted 只表示 ws 提交动作成功，不声称服务端已收/已落盘。

复核项（revalidateLeaseCommit）：取消/阶段 → send_cancelled；租约归属 →
lease_lost；连接代次（onopen/onclose 递增）→ connection_changed；会话定位器/
投影矛盾 → session_identity_mismatch；模型变更 → model_changed（retryable）；
插话目标 run → run_ended/run_changed。session_deleted 需要证据：sessions[]
非空且投影/定位器/当前会话三者皆无（`identityFreshlyCreated` 豁免——
ensureSession 刚返回的身份，投影可能尚未回流，S14/#2078）。

清理时机（P2.4）：`composerRevisionsByKey`（input-slice），setDraft（内容实际
变化）/附件增删/引用增删/文档上下文开关递增；onCommit 只在「修订号未变且身份
一致」时清理输入。快照文本不 trim；判空用修剪副本。

队列项 = 快照持有者：transport_submitted 前绝不移除；blocked/failed 原位标记
（status/errorCode/retryable），自动调度不无限循环也不跳过队首；编辑 = 取消
在途准备 + snapshotVersion 递增 + 回 ready；删除 = 取消 + 移除；显式重试复用
同一 queueItemId → 同一 clientMessageId → 同一逻辑记录（乐观消息 upsert 不
产生第二条用户消息）。版本守卫丢弃迟到结算。

插话门禁（P3.4）：`resolveQueuedInsertNowAction` — 活跃 run + 无 agentMentions
→ interject；仅 turnPending（回执等待）→ wait（保留输入 + 明确提示）；
agentMentions + 流式 → review_forbidden（保留既有禁止语义）。

## 代码契约变更（有意为之，已取证）

- `confirmOptimisticUserMessage`（chat-slice.ts）：回执/恢复回放合并时**本地
  文本优先**（本地非空则不覆盖）。理由：F1 输入所有权 + F10 保真——服务端
  持久化的本就是同一份 wire text（P7.4 禁止服务端 trim 替代正文），出现分歧
  时以用户原文为准。旧契约「服务端文本覆盖」只在服务端改写正文时可观测，而那
  正是 F1/F10 要消灭的情形。ws-message-handler.test.ts 的既有用例已同步更新
  并注释。
- `findSendRecordByClientMessageId`：同一 clientMessageId 可横跨多条记录
  （队列项取消/编辑后重试复用身份）；优先返回 awaiting_ack/delivery_unknown
  的活跃记录，否则最新一条。修复了「ack 命中已结算旧记录、活跃租约永不释放」
  的真实缺陷（Q11 暴露）。
- `QueueFlushDeps`/`dispatchQueuedItem`/`flushQueuedHeadNow`/`requestQueueFlush`
  （400ms 仅视觉缓冲，触发时重新验证全部门禁并同步取租约，不把时长当正确性
  条件）。

## 测试设计修正记录（红→绿过程中发现，均为测试自身缺陷，非削弱断言）

- S02：音频模型缺少原生 audioTransport 声明（evaluateChatAudioSendPreflight 无
  通用档回退）→ 模型条目补 `audio: true, audioTransportSupported: true`；第二个
  seedSession 会清空队列导致队首阻塞语义无法观测 → 重构为「队首失败项阻塞后续
  自动调度 → 用户删除失败项 → 音频项才被调度」，与 P3.3 语义一致。
- S05：门控读取 mock 每次调用重赋 release，第二段读取永不解决 → 改为按调用
  次序的 gate 持有者；session_deleted 布景按软化后的判定补齐「sessions 非空 +
  非当前会话」证据。
- S10：回执看门狗需要 fake timers，但全局 fake timers 会卡死 render 用例的
  waitFor → fake timers 收缩到 S10 局部。
- S12/S13：重试/模块级发送后租约仍在 awaiting_ack，后续派发被正确判
  transport_busy → 补 dispatchAck + endTurnPending（这是特性不是缺陷）。
- S13 渲染级：serializeEditor 对整体输出做边缘 trim（editor-serializer.ts
  L184）是 F10/P7 明文移除范围（任务书 P7.3），S13 渲染级改为断言「发送链
  逐字符传递序列化输出」并固定当前序列化契约，留注释要求 P7 升级该断言。
- Q11：编辑路径后队首仍是 q-a，删除路径永远不会先准备 q-b → 重构为先把编辑后
  的 q-a 正常发出+回执，再进入删除路径。Q12：首次插话后补回执释放租约。
