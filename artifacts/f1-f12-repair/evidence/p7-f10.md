## 实现

### editor-serializer.ts

- **serializeEditor 去 trim（原 L184）**：`lines.join('\n')` 原样输出；空白判空是调用方
  独立谓词（InputArea `composerPayloadIsEmpty`/`hasContent` 用 trim 副本，本就分离）。
- **空 paragraph = 可见空行**：参与序列化不再被丢弃；例外——徽章独占段（skill/file/
  session/agent badge）胶囊化呈现，不产假空行。
- **文档末尾真空段剥离**：TipTap 对列表结尾强制补一个空 paragraph（schema 垫尾，非用户
  输入），仅剥文档末尾的连续真空行；粘贴保真走段内 hardBreak 模型，不受影响（P01–P04
  往返零丢失为证）。
- **列表 hardBreak 续行缩进**：列表项段内的换行按 marker 续行缩进序列化（与多段列表项
  既有语义一致），列表不拆项。
- **新增 `insertFaithfulPasteAtSelection(editor, text)`**：粘贴的实际 insert 操作改为行内
  节点序列（text + hardBreak）插入当前选区——段落中间粘贴/选区替换不多生段落换行，
  空编辑器与列表项内不拆块；CRLF→LF 归一，`<tag>` 不进 HTML 解释（与
  buildFaithfulPasteContent 同族原语；听写插入在 P5 已复用后者做段尾追加）。

### InputArea.tsx

- 粘贴纯文本分支改调 `insertFaithfulPasteAtSelection`；富 URL 分支（extractPlainUrlPaste）
  优先级不变，普通多行含 URL 文本不进链接分支（P09）。

### message-parser.ts（P7.4 后续入口审计）

- `parseUserAttachments` 末尾 `join('\n').replace(/\n+$/,'').trim()` 的正文边界 trim 移除：
  协议标记行摘除后剩余正文逐字符保留（P12：首尾空格/tab/空行与落盘一致）。
- 协议附加块（[附件]/[参考文档]/[引用片段]/[attached_*]/[SessionFile]/[当前书桌目录]）被
  摘除时，同步摘除其前面的分隔空行——那是发送链 `\n\n` 追加协议块留下的系统残渣，
  不是用户输入（4 个既有用例因此从「正文带尾巴 \n」恢复为干净断言，非放宽）。

### 服务端核查（P7.4）

- `server/routes/chat.ts` prompt 路径：`promptText = msg.text || ""` 无 trim；技能调用按
  协议前缀追加（`[Use skill: x]\n`），与历史解析侧对称。chat.ts 其余 trim 均为 ID/label/
  reason 规范化，不涉正文。`composer-send.ts`：`finalText = text`（原文）+ 协议追加块
  （文件块/引用块/文档块），displayMessage.text = 原文；排队编辑
  `updateQueuedTurnInputText` 同步更新 item.text 与 bundle.text（无 trim）。

## 设计取舍（如实声明）

- 文档末尾真空段（schema 垫尾）被剥离：与「列表结尾消息」的既有序约一致；用户在结尾
  显式回车产生的末尾空行若恰逢系统追加协议块，其分隔空行一并摘除（wire 格式无定界符，
  无法区分），粘贴保真（hardBreak 模型）不受影响。
- 直播渲染器对 Markdown 的视觉排版 ≠ 源文本改变：验收同时检查序列化源文本与渲染行为。
