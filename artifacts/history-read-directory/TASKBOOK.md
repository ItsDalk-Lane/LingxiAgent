## 1. 问题、后果与本次修复的终点

### 1.1 已发现的问题

普通历史路径经 `loadSessionHistoryMessages()` 读取会话；Pi 路径包含文件修复检查、SessionManager 打开、当前分支恢复和消息投影。路由随后还进行多组 origin、presentation、review、Run 边界、工具结局、输入消费等处理。分页窗口之外仍存在重复的全历史工作。[SRC02、SRC03]

仓库旧证据记录过 140 次助手调用规模 3 页约 7,075ms、1,000 次助手调用规模 21 页约 52,992ms。但该记录不是本任务基线，也没有隔离全部成本。旧长 Run 夹具存在 toolResult 与 assistant 重复 ID、toolResult 自引用 parentId；必须先修正夹具并证明实际读取路径，再测量。[SRC01]

当前会话文件并非整个生命周期绝对 append-only：修复与快照刷新存在整文件重写路径。因此不能仅凭 size 增大认定追加，也不能只在文件变短时重建。[SRC04]

公开 `revision` 当前是 `${stat.size}:${stat.mtimeMs}`。分支解析另有 `leafId`、`observedTailLeafId`、物理尾部等语义；消息响应还包含文件之外的状态。不得把一个文件 stat 签名当作整个响应和全部分支语义的证明。[SRC05、SRC06、SRC07]

### 1.2 用户可见后果

长会话连续翻页重复读取旧内容，延迟和解析开销累积；同步读盘及 CPU 工作还可能影响同进程其他请求。错误的缓存或增量实现则可能造成跨分支混页、工具归属错位、Run 结局错误、展开重内容失败，或者把后补状态长期留在旧值。

本任务不是“让测试显示更快”，而是消除可重复定位的工作量，同时不制造以上语义错误。实际延迟主因由阶段 A 分项测量决定，不预先断言全部耗时来自 JSON 解析。

### 1.3 成本模型

统一使用以下变量：`F` 是文件字节数，`M` 是物理条目数，`N` 是可展示记录数，`K` 是页大小，`Dpage` 是当前页必须补读的依赖，`G` 是既有响应要求返回的会话级数据。

旧重复全量部分约为 `ceil(N/K) × O(F + M)`。只有平均记录大小与结构比例固定时，才可简化为近似二次增长。

目标是冷构建承担一次全量成本；稳定热页只承担定位、窗口及必要依赖、既有会话级响应与外部状态成本。可信追加只读取新增字节及必要尾记录，并更新受影响的关系。

不要承诺任意数据集的整个 HTTP 响应均为 O(K)。若 `sessionFiles` 等既有字段随会话规模增长且每页必须返回，这部分成本必须单列，不能删除字段来满足性能数字。

## 3. 必须保持的不变量

**I01：身份与授权先于缓存。** 每次请求先按现行逻辑解析 sessionId/path、检查路径与权限；命中缓存不跳过授权。缓存不能跨 runtime、studio、会话或 locator 绑定污染。

**I02：坐标不混用。** 物理字节位置、物理条目、分支条目、`sourceIndex`、`displayIndex`、页内 `afterIndex` 分别定义。`sourceIndex` 保持现有“分支条目转换与过滤之后的 sourceMessages 下标”语义，不能换成行号或局部数组下标。

**I03：同事实同输出。** 在相同请求、身份、文件/分支快照和外部状态下，缓存开/关及重建前后结果一致。正文、块顺序、游标、entryId、sourceIndex、Run 边界、工具归属、延迟凭证都不能变化。E 新增头部/概览字段仅按冻结的协议清单允许差异；显式相同 limit 的旧业务 JSON 仍逐字段一致。不同 limit 比较采用原始记录集合、顺序和完整归并语义，不比较不同窗口的整段 JSON 字节。

**I04：只有一套生产语义实现。** 冷目录、热目录、无缓存全量模式使用同一套归一化、定位规则和窗口投影函数。允许读取策略不同，不允许复制两套“缓存版/普通版”业务循环。

**I05：文件变化与分支变化分别校验。** 文件身份、stat、locator 与分支视图均参与内部有效性判断。分支头缺失和存在但 `leafId=null` 必须区分；`observedTailLeafId` 的含义不能省略。

**I06：不发布混合快照。** 目录构建和页面读取必须具有明确的已读边界及分支身份。读取中变化只能按已验证的追加快照处理，或重试/回退，不能给混合结果签发可复用缓存。

**I07：revision 不超前。** 维持公开 `${size}:${mtimeMs}` 的语义；响应 revision 不得声称已经读到实际未覆盖的新写入。读取后拿更晚 stat 给旧正文盖章是禁止行为。

**I08：未知就不命中。** revision 为 null 时不读旧缓存、不写新缓存，并令旧条目不可用。缓存缺失或损坏不影响正确性；但文件本身不可读不等于必须伪装成成功空历史。

**I09：半行不破坏。** 未完成尾记录不进入目录、不触发删除或重写文件；下次从其起点重读。合法无末尾换行记录与截断 JSON 分开处理。

**I10：追加可改变旧投影。** 追加引发的 Run 末端、工具结局、输入消费、协作决定及关联歧义必须更新。不得把旧 display 序号稳定理解成旧展示对象永远不变。

**I11：资源有界。** 缓存及其旧版本、Map、闭包、读取中的租约都受预算和释放机制约束；不得把正文藏在 helper 返回值或捕获数组中。

**I12：模式不降级。** 严格对账的证据等级、`all=1`、延迟展开、活动广播和会话级状态保持原有职责；不能因为分页缓存或 HTTP 校验存在就绕过它们。

**I13：304 只验证本次选中表示。** 先鉴权、确认有效请求并生成当前页面事实，再比较完整表示校验器；文件 revision 相同不等于可返回 304。目录、外部状态或投影失败不能被旧 ETag 遮盖。

**I14：有已应用表示才可条件复用。** 客户端只有在对应 200 已成功进入当前会话状态且相关状态未失效时，才附带 ETag。没有持有可用数据的 304 不能变成空历史，应有界无条件补取。

**I15：建议不拥有分页事实。** 概览条数、页数估计和推荐 limit 不取代 messages 响应的 hasMore/nextBefore，不取代 Run 合并和结局裁决。概览失败不阻塞首屏和翻页。

**I16：渐进互操作。** 新旧服务器与新旧客户端四种组合均可使用；能力不明、不支持、头部不可见时保守走原有请求方式。401/403 不是功能缺席，不可吞成普通降级。

**I17：收益分别归因。** B/C 消除服务端重复历史工作，E 条件校验减少传输/重复解码，概览减少探底请求，页大小减少翻阅往返。不能用其中一项的数字替另一项验收。

## 4. 目标结构与模块责任

建议在 `server/history-read/` 建立局部模块，目录名可遵守仓库既有命名，但职责不得合并成第二个巨型路由。

| 责任 | 输入 | 输出与限制 |
|---|---|---|
| `captureReadContext` | 已授权请求、现有 engine | 业务身份、规范 locator、分支头状态、公开 revision、内部文件校验信息；不得为取令牌而全读 JSONL |
| `scanHistoryFile` | 文件句柄、已捕获长度、起始偏移 | 原始字节位置与逐条归一化事实；只读、正确处理 UTF-8 和尾记录 |
| `buildHistoryDirectory` | 扫描事实、分支上下文 | 紧凑文件索引、当前分支视图、关联索引、会话级事实指针 |
| `resolveHistoryPage` | 目录、现行 before/limit/all 参数 | 既有页边界、所需记录及依赖定位、页首投影上下文 |
| `readHistoryRecords` | 经验证的定位与文件句柄 | 本请求临时使用的完整记录；不重新编号，不长期驻留 |
| `projectHistoryPage` | 页面事实、关联事实、既有 projector | 当前协议的 messages/blocks；不重新扫描全部历史 |
| `hydrateExternalState` | 本页及必要会话级引用、engine | 现行 deferred/subagent/workflow/sessionFiles 等实时补充 |
| `HistoryDirectoryCache` | 稳定会话键、目录版本 | LRU、预算、single-flight、失效、原子发布与释放 |

目录在逻辑上分为“物理文件索引”和“当前分支投影视图”。分支变化可以复用仍有效的物理偏移，但必须重新建立分支视图；不要求任意分支切换都是 O(1)。

`disableCache` 是内部依赖注入/测试模式，不新增公开 query 参数。关闭缓存后重新建同一目录、调用同一 projector，不走复制的另一套语义。

阶段 E 在上述结构外只增加局部协议层：页面响应序列化/ETag 工具、概览投影函数，以及客户端历史请求控制器。协议层不重新实现 JSONL/分支扫描，目录构建器不负责 HTTP 条件头，chat store 不成为服务端事实源。

# 阶段 B：稳定快照下的目录缓存与定点读取

## B01. 先抽取同源语义，再加入缓存

从现有加载/路由中抽取以下共用能力：原始条目归一化、消息可见性、source/display 坐标生成、Run 与输入指针、关联事件处理、pageBounds 和窗口 hydrate。

不要重写判定规则。特别保留 Reminder 清理后的显示语义、隐藏 user 占 display 序号的行为、不可见 assistant 对当前 assistantOrdinal 的既有影响、loop/custom input、legacy tool failure 与 origin/presentation 的覆盖次序。

分支选择复用或抽取现有 `projectCurrentSessionBranchEntries` 的选择规则。允许把纯分支选择与完整 lineage hash 计算分离，但不改现有完整分支 API 的结果，不用删去正文的假 entry 调用需要正文的哈希逻辑。

此步先用无缓存全量事实运行同一新 projector，逐项对比 A04。语义不等价时先修正抽取，不能继续叠加缓存排查。

## B02. 实现只读扫描与完整记录边界

以原始 Buffer 统计偏移，不使用 JavaScript 字符串长度、重新 JSON.stringify 后的长度或过滤后的行数计算位置。

扫描器记录 `byteOffset`、`byteLength`、行分隔长度及物理条目身份。支持分块扫描、中文/emoji、CRLF 和跨缓冲区字符。冷构建允许读取全文件，但不要同时长期保留原始大字符串、全部 parsed entries 和全部 projected messages。

分别维护：

```text
observedFileSize      本次捕获的文件长度
indexedThroughOffset 已安全处理的记录边界
pendingTailOffset    未完成尾记录起点；没有则为空
lastUndelimitedRow   合法但无末尾换行的末条定位；没有则为空
```

完整末条 JSON 即使没有换行，也按兼容语义处理；记录其特殊尾状态，下一次文件变化时从该条起点核对或重读，避免多出/漏掉一条。截断 JSON 或不完整 UTF-8 的尾部不进入目录，后续从 pendingTailOffset 续读。

不能把所有 JSON.parse 失败都当作“暂时半行”：已完成位置的损坏、重复 ID、缺父节点和环必须按明确错误/兼容规则处理并留证据，不建立正常快路径目录。

读取时不调用会删除半行的修复函数，也不因目录故障调用可能破坏尾部的旧路径。现有大条目归一化若影响正常响应，应复用现有纯投影规则；对应原始偏移始终属于原文件，不把投影后字节长度当文件坐标。

本任务不修改全项目维护策略。正常稳定文件的响应等价是硬要求；需要迁移或修复才可解释的异常格式进入已核实的兼容范围，不能悄悄用物理线性扫描取代 v3 当前分支。没有可证明分支的文件不得拼接多条分支返回。

## B03. 建立目录与页面依赖闭包

目录只保存小型定位或语义事实。按需要包括：

```text
文件级：文件身份/校验信息、字节边界、物理尾 ID、entryId→物理位置
分支级：分支头是否存在、leafId、observedTailLeafId、选中 leaf
坐标级：分支条目↔sourceIndex↔displayIndex
记录级：role/type、可见性标志、entryId/parentId、Run 引用、必要序号
关联级：toolCallId、deliveryId、taskId、输入/助手引用、关联事件指针
会话级：最新合法 todo 快照指针、活跃文件引用集合、必要媒体结果指针
```

所有长文本、工具参数/输出、完整 review/presentation 对象、parsed block、媒体内容等只保存原记录引用，按页临时读取。不能把 `collectToolOutcomesByCallId` 含输出的完整结果 Map 直接塞进长期目录。

原始分支 custom 中的桌面输入 correlation 必须在消息过滤前纳入事实；保留“一对多/多对一导致 ambiguous”的规则和后补冲突更新能力。

Run 记录指向共享的小型边界描述，而不是要求一次追加改写该 Run 全部消息对象。页首需要的 latestTurnInputEntryId、visible、assistantOrdinal 等上下文必须从索引直接得到，不能每页从根重放。

依赖闭包须按 A02 表逐项接线：页内消息、页外工具结果、前置注释事件、后置消费/决策、必要 custom/interlude、媒体最终结果、todo 指针以及活跃文件引用。索引须支持按页面范围定位 block 锚点，不得每页 `filter` 全部 block 锚点。

todos 使用当前分支“最新合法快照”的指针，保留坏快照跳过、空快照显式清空的规则，禁止改为物理尾部猜测。

sessionFiles 保留原有当前分支引用语义。抽取现有引用识别器，将紧凑引用集合传给现有 registry/适配入口；不能只传本页正文致使旧文件从列表消失，也不能每页重新扫描全部正文提取引用。

冷构建允许少量元数据线性遍历。禁止为追求字面“一遍循环”将全部逻辑并成复杂巨型状态机。热页不允许全历史/全目录线性扫描。

## B04. 建立缓存身份、预算与发布规则

缓存归属当前 route/runtime 实例；使用稳定会话键，内部绑定规范 path 和文件身份。存在业务 sessionId 时纳入 runtime/studio 命名空间和 sessionId；兼容路径必须有明确路径命名空间，不共享空 key。

内部文件校验信息至少包含经平台验证可用的文件身份（例如 dev/ino）、size、mtime 与 ctime；支持时可使用更高精度时间。明确哪些平台字段不可用及其降级规则。路径打开后的 fstat 与必要的路径复核不能省略。它们能加强失效探测，但仍不构成任意外部写者不改旧前缀的绝对证明。

每个稳定会话槽保存当前目录版本，而不是每个 revision 单独占一个 LRU 槽。目录内保存公开 revision、内部文件校验信息、locator 绑定与完整分支状态。仅比较会影响语义的分支字段；不要为了取分支令牌每页打开全量 SessionManager。

本任务初始资源预算如下，属于验收配置，不是既有测量结论：

```text
maxSessions = 8
maxResidentIndexBytes = 64 MiB
maxSingleDirectoryBytes = 16 MiB
maxConcurrentBuilds = 2
maxConcurrentReadsPerPage = 4
```

缓存命中提升 LRU 次序。超预算淘汰可释放的最久未使用条目；单目录超过准入限制则走无缓存只读路径，不截断历史。预算统计包含 string/Map/数组等结构的保守成本，明确估计口径，并通过实际驻留测量验证；JSON 序列化大小不是 heap 大小。

在途请求持有的旧目录版本不能在计数中凭空消失。旧版本仍被引用时计入驻留预算；不能同时插入无限新版本。构建临时内存单列测量，限制并发；不宣称整个应用进程内存被这 64 MiB 覆盖。

同一会话同一版本并发 miss 共享一个构建任务。失败任务从 in-flight 表移除；构建成功且校验通过后才发布。旧任务晚完成不得覆盖新版本。命中/重建/淘汰/销毁后的 Map、闭包和文件句柄都需释放。

## B05. 实现定点读取与原坐标 hydrate

根据页内记录及依赖闭包取得离散字节区间，按物理位置排序、去重。默认只合并重叠或紧邻区间；若合并小间隙，必须有明确上限并记录额外字节。禁止读 `[最早依赖, 最晚依赖]` 整片大区间冒充窗口读取。

使用明确 position 的读取。检查实际 `bytesRead` 并循环补齐；遇到异常 EOF 时重新校验，不把未填充 Buffer 当有效 JSON。所有正常、异常、取消分支均关闭句柄。[SRC11]

同一请求内重复引用的记录只解析一次。解析后检查实际 entryId/type 与目录一致；索引校验失败触发本会话失效，不能继续拿错行投影。

使用能保留原 sourceIndex 的读取视图或显式 locator 适配，不把稀疏事实重新编号成零起点数组。不要为兼容旧数组 API 每页复制 N 个元素；可以调整内部 helper 参数，但不得改对外 sourceIndex 或延迟内容凭证格式。

仅将本页完整记录和必要依赖临时传给同源 projector。一行 JSON 内有大载荷时，当前行完整解析可能仍需读入该载荷，这是必须报告的读取粒度；不能宣称“50 条消息就固定读取 400 KiB”。

超大行不是提高缓存上限、增加截断或悄悄内联全部内容的理由。保留既有正文与延迟展示行为，单行及响应内存开销分别报告。

## B06. 快照、变更与回退

请求基本顺序：

```text
现有身份解析与授权
→ 捕获 locator、分支状态、公开 revision 与内部文件校验信息
→ 查缓存/合并构建
→ 解析页窗口和依赖
→ 在已捕获边界内读记录并验证
→ 同源投影
→ 按既有方式补充外部状态
→ 必要的文件/locator/分支复核
→ 返回与已覆盖内容相符的 revision
```

读取前后应能区分稳定、可信追加与其他变化。文件句柄的身份与路径当前所指文件身份都要考虑；一个仍可读取的旧句柄不自动代表当前 locator 仍指向它。

阶段 B 中任何无法证明为同一稳定视图的变化均失效重建；阶段 C 才启用可信追加。捕获后发生的合法追加可以延后到下一次请求，但必须明确返回旧已覆盖快照，不能挂上新 revision。

最多进行 2 次一致视图尝试；目录损坏先失效并重建一次。仍失败时执行不使用旧目录的安全只读全量读取；该回退同样有一致性校验，不能无限重试。成功则返回正确结果并记录降级；无法确认分支/文件一致性或真实 I/O 失败时，使用既有可诊断错误处理，不返回旧页或伪造成功空历史。

正常半行且可证明当前分支完整前缀时返回完整前缀，不报“整份历史损坏”。若持久化 head 指向尚未可见的条目，只有能证明安全前缀属于同一选择时才返回它；无法证明则进入明确的不完整/错误路径，不能取另一条分支补齐。

日志至少包含内部会话标识、阶段、失效原因、前后版本摘要、重建/回退次数，不包含正文或工具输出。重复错误可聚合，但累计计数必须保留。

推荐原因枚举：`revision_unknown`、`file_identity_changed`、`branch_changed`、`locator_changed`、`untrusted_mutation`、`directory_invalid`、`short_read`、`tail_incomplete`、`budget_exceeded`、`legacy_fallback`、`snapshot_changed`。正常追加不是 error。

## B07. 接入既有路由，保持特殊模式与外部状态

普通分页是本阶段必须启用的生产路径。不得只在测试中实例化目录模块。

`all=1` 维持全量返回，可使用同源全量模式；不套用窗口大小性能断言。不将正常客户端改成强制 all。

`reconciliation=1` 在 A—F 全部阶段保留现有严格证据路径，不以普通目录命中或普通页面 304 代替验证。任何共用 helper 调整都必须回归其业务身份、SDK 头身份、分支、runRevision 和 complete 判定。不扩展本任务为“对账加速”。阶段 E 的条件请求仅用于支持的普通历史分页；all 与 reconciliation 不进入该条件快路径。

`/sessions/content/:contentId` 不要求本次性能优化，但必须验证新页面产生的所有延迟凭证仍能在该既有端点正确展开。授权、entryId 校验、kind/ordinal 全部保留。

find、其他历史调用者不强制迁移到新缓存；抽取共用函数不能改变它们的行为或 source/display 坐标。

deferred、durable subagent/workflow、session file lifecycle 等继续从原事实源读取。缓存里只存关联定位，不把它们的可变展示状态冻结在 JSONL revision 下。

核对旧普通读取在 `applyStoredSessionBranchHead` 等边界执行的 manifest backfill/append recovery。若这些副作用属于现有生命周期契约，必须由现有协调器在已验证上下文中幂等完成，并以生效后的 head 校验/发布目录；不能为热页每次重开全量 SessionManager，也不能悄悄取消恢复职责。严格 reconciliation 不因此获得这些副作用。恢复建议已过期时不得覆盖较新的显式分支选择。

首屏活动 rebroadcast 的条件和次数保持现状。side effects 位于目录重试之后，每个成功请求按原规则触发一次，不能每次构建/重试都重复广播。

## B08. 阶段验收

执行全部定向语义差分、稳定页性能、目录与编码、权限和特殊模式测试，再生成 phase B 数据。达到第 7 节 B 阶段指标才进入 C。

必须证明：稳定快路径热页 `fullFileReadCalls=0`、`fullHistoryProjectionCount=0`、fallback=0，解析量和元数据访问量来自页面依赖而非全历史；页外正文未长期驻留。

# 阶段 C：可信追加与受影响事实的增量更新

## C01. 建立变化分类，而不是 size 判断

实现以下决策表，并逐项测试：

| 观察结果 | 处理 |
|---|---|
| 身份/locator/分支语义/文件版本均有效且未变 | 复用目录 |
| 已证实旧前缀不变的正常追加 | 增量续读 |
| 追加发生在被丢弃旧分支 | 更新物理索引，按现有 head 规则决定是否改变当前视图 |
| 文件不变、分支选择改变 | 保留有效物理索引，重建当前分支视图 |
| 文件缩短 | 全量重建 |
| 同长度内容重写 | 全量重建 |
| 重写后比原文件更大 | 全量重建 |
| 同路径底层文件替换 | 全量重建 |
| locator/业务绑定变化 | 失效、重新解析并保持授权语义 |
| 无法区分追加与重写 | 全量重建 |
| stat 失败 | 不用缓存、不写缓存、按安全路径读取或报错 |

公开 revision 不变而内部识别到文件替换/分支变化时，仍不得复用旧目录。内部校验不是新增对外 revision 协议。

## C02. 为生产追加路径建立可信依据

以 A02 写入清单为依据，在必要的现有应用层边界维护内存失效世代/变更通知。只作缓存提示，不成为新的持久化事实源。

重写失效必须在旧偏移可能变得无效之前可见，不能只在写完后才通知；写失败也不能把旧目录重新标成可信。locator、删除和分支操作同样处理。

启用可信增量必须同时有：旧文件身份有效、旧记录边界有效、已知写入模型保证旧前缀不被改动、通知覆盖全部受支持的重写路径、分支语义可解释。保留每次 stat/身份检查，不能仅靠 fs.watch；抽样哈希也不能被描述成完整旧前缀不变证明。

如果多进程/外部写入没有统一权威通知，则这些路径不承诺增量；检测到变化时全量重建。任意外部写者能够改写未读取前缀时，不允许仅凭尾部样本保证正确。

需要在报告中明确支持与不支持的并发写入模型。在无法同时获得一致性证明和当前范围允许的改动时，禁用受影响快路径，保留 B 收益，并把 C 对应验收列为受阻。禁止为了全绿开启一个只能依靠测试桩“保证追加”的生产路径。

本任务不要求在抵抗任意外部恶意篡改的同时仍获得常数热页成本。不得掩盖信任边界；不满足已声明文件稳定性条件的来源应安全降级。

## C03. 增量扫描与尾记录合并

从 `indexedThroughOffset` 或待重读末条起点续读，不从上次 observedFileSize 盲目续读。文件新增了后半行时必须合成完整记录，不重复之前已纳入的条目。

在同一构建器的增量接口中处理新增事实，更新物理 ID 索引、branch/source/display 序号、依赖与状态指针。不要另写一套 append 业务判定。

以新条目的 parentId 检查它属于当前分支延续、其他分支还是非法结构；新条目并不自动计入当前 display 总数。head 存在且为空、observedTail 变化和 append recovery 全部遵守原规则。

对于长序列，不得每次 append 都复制完整 Map/数组、重新遍历旧分支或重做全部 lineage hash。使用分段结构、有界尾状态、必要的小型 copy-on-write 等方式；具体选择在报告中给出计数证据。

新版本目录发布前重新验证版本/分支。已有请求持有旧版本时看到的是完整旧快照，不能被原地修改的 Run 结束位置或 Map 内容污染。

## C04. 更新会反向影响旧页面的关系

逐项实施并验证：

| 追加事实 | 必须更新 |
|---|---|
| 开放 Run 新增 assistant | Run 边界；重新读取旧页时得到新的 turnEndIndex |
| 旧 toolCall 的结果 | 工具状态、结果定位、结束时间；旧页不得永久 unknown |
| 输入消费事件 | 目标 assistant 的输入归属、interlude 锚点和去重结果 |
| 协作决定 | 目标建议卡最终状态 |
| 客户端输入关联冲突 | 相关旧 user 的 ambiguous 诊断 |
| origin/review/presentation/modelCall 前置事件的后继消息 | pending 状态正确消费，不丢失跨追加边界关联 |
| 媒体最终记录/状态事件 | 对应任务展示和必要 standalone 锚点 |
| todo 合法、坏或清空快照 | 当前分支最新合法指针及清空规则 |
| 文件引用记录 | 当前分支活跃引用集合 |

复杂度按“新增字节 + 新增条目 + 受影响关系”验收，不要求所有语义更新严格只有 O(新增字节)。普通追加不能把无关旧正文重新解析一遍。

## C05. 增量性能与真实路由验证

在已建立 1k 和 10k 目录的相同结构会话上，分别追加相同数量/字节量的合法记录。至少覆盖 1 条、10 条、100 条以及一条大工具结果。

记录新增字节、尾记录重读字节、验证字节、解析条数、旧元数据访问数、受影响关系数和更新时间。两种历史长度的新增工作量应由增量决定，不由旧历史大小决定。

另在超长开放 Run 上逐条追加，检查没有每次 O(Run 长度) 的批量改写、全 Map 复制或重新投影。至少一个增量用例必须通过真实生产写入/分支同步入口触发，再由真实路由读取，不能全是手工 append 加假通知。

以阶段 C 命令输出原始数字。P12 的通过需要生产快路径证据；单元测试模拟可用于覆盖异常，不替代生产接线证据。

## 5. 故障恢复、兼容边界与分支分页限制

### 5.1 不能以“旧路径”为万能正确性证明

仅目录损坏而原文件完好时，应能重建得到正确结果。原文件本身损坏或身份未知时，不能以“保持老代码成功空数组”为理由声称已正确恢复。

新读取异常不得触发破坏性修复半行，也不得在 v3 分支解析失败时直接把全物理文件线性消息返回。旧格式按已核实的兼容 parser 处理；无法安全解释的情况显式降级或错误，不能混分支。

这些异常语义与旧路径若存在差异，逐项写进兼容报告。正常合法文件与既有分页语义不允许差异。

### 5.2 单请求分支一致与跨请求前端一致分别验收

服务器必须保证每次响应使用同一个被选中的分支视图。

跨页期间用户重试/切分支后，前端已有旧页是否清空，需用既有分支操作与真实 store 验证。缓存 key 含分支不代表前端旧页自动消失。

本任务不新增分支游标协议，也不把 branch token 塞进 nextBefore。若现有前端生命周期不能阻止跨分支混页，记录为独立前置缺陷，标明端到端验收受阻，不重写 Run 合并规则来掩盖。

外部在客户端不知情时切换分支、而请求仅带裸 before 序号的情况，不能宣称由纯服务端目录或 ETag 完全解决。本任务的 E 授权覆盖已知重试/分支操作后的请求与校验记录失效，不包含建设跨请求不可变快照或改变 nextBefore 的协议。对于没有既有通知的外部分支变化，继续明确报告当前端到端保证的边界；不要把页面 ETag 当成分支游标。

### 5.3 降级边界不能掩盖热路径失败

合法正常稳定 v3 性能夹具不得走 fallback。异常格式、超预算、多进程未知变化可以安全降级，但必须记录覆盖范围和命中率。

不能把每次追加都降级重建却宣称 C 完成；也不能把冷构建/外部状态全量成本藏在不统计的 helper 中。

## 7. 性能与资源验收标准

以下是本任务设定的初始验收预算，不是对当前机器的性能预测。阶段 A 开始前写入 `acceptance-budget.json`；不得看到失败后自行放宽。发现阈值与输出固有规模矛盾时记录受阻及数据，不能删字段或更换更轻夹具。

### 7.1 工作量硬条件

对合法、未变化、已预热且未超预算的正常 v3 页面：

```text
fullFileReadCalls = 0
fullHistoryProjectionCount = 0
fallbackCount = 0
```

`jsonlParseCount` 必须等于实际需要读取的去重记录数量；每个已读取记录只解析一次。任何额外解析有明确且有界的原因，不得随旧历史 N 增长。

定位元数据访问量应为 `O(log N + K + |Dpage|)` 或更好，不能每页全量 `.filter/.map` 目录。会话级 G 的读取与输出另行计数。

窗口逻辑读量应能用“实际读取的记录行总字节 + 文件/边界验证字节 + 有界合并间隙”逐项解释。单页可包含大行和非局部依赖，不硬写成 K 乘固定字节数。

### 7.2 延迟与规模条件

固定短载荷、固定工具比例、固定外部状态大小的参考夹具：

```text
热页：p50_10k <= 3 × max(p50_1k, 5ms)
冷页：p50_new <= 1.25 × p50_baseline + 25ms
全翻：total_10k / total_1k <= 15
```

同时报告 p50/p95/max、样本数和原始请求数据。以上阈值是宽松回归门槛，不是把“接近 3 倍”描述成“比值接近 1”。实际数值必须完整展示。

冷页测试的 cache-cold 必须通过新的缓存实例或明确清空完成；不得把 OS page cache 未清空的测试称为物理冷盘。大基准不与其他高负载全量测试同时运行。

A—D 的服务端 benchmark 不以真实网络为前提；D07 另行建立真实 HTTP/客户端传输基线，F02 测最终端到端链路。Hono 内存耗时、HTTP loopback 和经受控延迟链路的结果分别记录，不能混入口径。

### 7.3 增量条件

固定新增记录/字节在 1k 和 10k 两种历史上，新增读取/解析条数应一致或仅有明确尾记录差异；增量元数据访问量由实际受影响关系解释，不能包含整段旧历史。

每次追加重新复制整个目录、重新全分支 hash、遍历全部 tools/tasks/blocks 的行为，不能列为“增量已实现”。

### 7.4 内存条件

报告 1k/10k 单会话、8 个会话共存、超过 8 个轮换、单目录超预算和并发构建场景。给出驻留估计与 heap/external/arrayBuffers/rss 差值，区分目录、临时 hydrate 与前端 chat 缓存。

采用带唯一大载荷标记的 fixture，检查目录可达对象没有正文、原始 JSONL Buffer、源消息数组或携带完整输出的 Map 值。还要确认淘汰后无闭包/监听器维持引用。仅检查字段名或序列化大小不够。

目录缓存上限不等于系统响应绝对内存上限；超大单行和既有 all 响应的开销如实列出，不新增隐性截断。

## D02. 三份类型检查与全量回归

执行：


# 阶段 E：正式实施协议层配套

本阶段已获授权，不再是附录或可自行略过的建议。按 E01—E08 实施，前提是 D07 技术闸门成立。E1/E2/E3 分别指条件校验、概览、页大小这三项产品目标；E01—E08 是下面的执行步骤。

## E01. 冻结协议合同与收益边界

新增 `protocol-contract.md`、`protocol-dependency-matrix.md`、`protocol-acceptance-budget.json`。先写清请求/响应与回退规则，再写生产代码。名称在本任务书中作为默认执行方案；若仓库已有完全相同职责的接口/类型，复用它并记录一对一映射，不能并存两套协议。

本次采用以下最小合同：

| 项目 | 冻结规则 |
|---|---|
| 原消息端点 | `/api/sessions/messages`，现有业务 JSON 字段和 nextBefore 含义不变 |
| 版本声明 | 新服务端在普通成功消息响应中声明 `Lingxi-History-Protocol: 1` |
| 条件校验 | `ETag` 响应头、`If-None-Match` 请求头；只验证相同普通页面请求 |
| 页大小建议 | `Lingxi-History-Page-Limit: K` 响应头，K 为 E06 实测选出的推荐值 |
| 新概览端点 | `GET /api/sessions/history-overview`，复用 sessionId/path 解析与 sessions.read 授权 |
| 公开 revision | 继续使用原文件 revision，不替换格式、不赋予响应级语义 |
| 兼容默认 | 未传 limit 的消息请求仍默认 50；所有请求上限仍为 200 |
| 304 资格 | 只有成功、可解释的普通页面；all/reconciliation 不使用本协议的条件快路径 |
| 私有数据 | 200/304/概览采用 `Cache-Control: private, no-store`；客户端显式条件请求使用 `cache: 'no-store'` |

版本和页大小声明是能力/建议，不是访问凭证、分支身份或完成状态。旧客户端不发送条件头时仍得到正常 200 和原 JSON；新客户端看到缺失、不支持的版本或不可读头部时，按现有 50 条请求和 200 处理回退。

E1 的第一版明确采用“当前页面完整投影后生成 ETag”，不要求建立跨所有外部 store 的新全局 revision 系统。也就是说，服务端仍通过 B/C 读取本页和必要依赖、读取现有外部状态，得到当前响应后再比较摘要。它节省的是正文传输和客户端重复解码/应用，不宣称省掉本次页面 hydrate 或摘要计算。

不实施“先看 file revision 就直接 304”。不为追求提前 304 扩大到全仓各类 store 的版本化改造；以后需要更便宜的预校验再独立评估。完整页面必须来自 B/C 路径，不能为算 ETag 恢复到整会话全量读取。

合同至少列出以下状态转换的确定行为：首次加载、同页重复校验、新页加载、文件追加、同长度重写、分支切换、外部状态改变、客户端收到 WS、客户端会话被淘汰、鉴权失效、连接切换、服务器重启、旧服务器缺少概览/头部。不得只列稳定 200→304 的理想路径。

## E02. 实现服务端条件 GET

### E02.1 在正确边界生成当前表示

在原消息路由的成功返回边界接入，不在授权之前、不在目录命中处接入。步骤固定为：

```text
原身份解析 / 授权 / 请求校验
→ B/C 当前页和依赖读取及快照复核
→ 原 projector + 原外部状态补齐
→ 完成本请求原有且适用的 lifecycle/rebroadcast 行为（仅一次）
→ 确定本次成功响应体和协商头
→ 序列化当前页面一次，计算有作用域的 ETag
→ 合法条件匹配：304，无正文
  否则：200，发送刚才序列化的原响应体
```

正常成功请求的活动广播不能因为响应最终为 304 而被无意取消；也不能因为内部重试重复广播。由此前广播造成的 WS 到达客户端时，客户端按 E03 的版本护栏处理。若广播、终态回填等让响应本身变化，允许得到 200，不为提高 304 比例删减业务行为。

表示校验覆盖所有响应业务字段：messages、blocks、todos、sessionFiles、hasMore、nextBefore、revision，以及未来合同清单明确保留的字段；不只 hash 消息正文。外部 store 本次读取所得字段进入当前表示，JSONL 不变但这些字段变化时必须不匹配。

在请求局部保留序列化字符串或 Buffer，200 复用同一字节串发送；不能先 hash 一套 JSON、再走另一套 serializer 发送不同表示。字符串/Buffer 不写入目录或响应缓存，请求结束释放。保持 UTF-8 内容、字段省略规则、数组次序、Content-Type 和现有中间件职责。

原消息响应中不新增当前时间/随机 snapshotId 来制造每次都不同的 ETag；也不能删去已有必要字段来制造命中。严格对账的随机 snapshotId 不在 E1 适用范围。[SRC07]

### E02.2 校验器生成规则

建议使用 Node 内置 crypto，对以下有界数据计算加密摘要：

```text
协议/序列化版本
+ 当前服务实例的临时作用域盐
+ 已授权主体/运行时/studio/业务会话及规范 locator 的作用域标识
+ 规范化请求身份（端点、before 的“最新页/指定值”、实际 limit、模式、语言等表示维度）
+ 本次目录确定的分支选择身份
+ 最终响应 UTF-8 字节
```

只纳入非敏感内部身份或其摘要，不把原始 bearer token、路径、正文、账号等编码进可逆标签。作用域盐是进程内随机值，不落盘、不改变持久化 schema；服务重启造成旧标签失配是正常回退，不要求跨重启保持命中。身份不可靠、revision=null、普通读取降级且无法保证表示正确时，不给该页签发可复用标签。

本次可采用 `W/"hrp1-<digest>"` 的不透明弱 ETag：摘要使用完整未压缩业务表示，保守处理下游 content-encoding。即使使用弱标签，也不允许忽略会改变业务含义的字段；使用弱标签不是容忍陈旧数据的借口。协议头语义和推荐 limit 的改变也纳入标签版本或身份，不让客户端长期持有不一致的协商元数据。[SRC13]

ETag 与 file revision 是不同职责，不修改 file revision。必须直接使用本请求目录提供的分支上下文，不为 hash 分支信息再次打开 SessionManager 或遍历整分支。

### E02.3 HTTP 行为

按 HTTP 条件请求语义处理合法 entity-tag 列表、弱比较和 `*`。官方新客户端只发送服务器返回的单个不透明标签，绝不发送 `*`；服务端面对外部合法 wildcard 仍先授权、解析和确认资源存在。边界超长请求按既有 HTTP 头部限制处理，不新造一个宽松安全入口。语法无效且未触发现有安全限制的条件值可以忽略并正常 200，记录测试。

只有本来会成功返回 200 的普通页面才能条件命中。403/404/500、文件读取失败、分支不确定均不能变成 304。缺条件头、标签过期、跨页标签或作用域不一致正常返回当前页 200，不强制 all=1。

304 必须无 JSON 正文，不能返回 `{notModified:true}`，也不能把空 messages[] 当作“不变”。正确设置 ETag、私有策略和对应的协商/Vary 元数据；不要把旧 200 的 Content-Length 错贴到 304 上，除非完全满足规范要求；本任务默认不设置 304 Content-Length。[SRC13]

all/reconciliation 客户端不发送条件头；服务端不让它们进入普通页面校验函数，按原完整模式处理。对这些模式的边界请求编写回归，确认严格证据不被 HTTP 快路径取代。

ETag 相关日志只含内部 requestId、结果、reason 和截短/不可逆摘要；不记录 Authorization、完整路径查询或响应正文。

### E02.4 服务端小型验证先于客户端接入

先用真实路由验证：首次 200、同表示匹配 304、页参数不同 200、追加后 200、文件不变但 task/file 状态变化 200、stat 失败不签发、授权拒绝不泄露标签。每个 304 用同请求的无条件 200 作为 oracle，比较实际当前 JSON；不能只比较两个 hash 值来证明 hash 逻辑自己正确。

## E03. 接入客户端条件校验与失效

### E03.1 复用既有请求与竞态护栏

先核对 `session-actions.ts` 中普通 loadMessages/loadMoreMessages 及其调用者、reload/force restore 的语义，区分“校验当前已加载表示”与“需要重建、恢复或补全状态”。只在前者有充分已应用证明时使用条件请求；强制恢复、流式修复、严格对账、新页面首次加载均无条件请求。[SRC15]

当前 `lingxiFetch` 默认对非 2xx 抛错，已有 `throwOnHttpError` 选项。仅历史协议调用使用 `throwOnHttpError:false`，在局部包装器中先处理 304 再处理其他状态。不得把全项目非 2xx 错误检查关掉，也不能直接绕过连接鉴权 helper。[SRC14]

显式传入 `cache:'no-store'`，继续传递原 abort signal、超时和连接鉴权。这样不依赖浏览器 HTTP cache 自动保存正文或把网络 304 合成为 200；应用只使用既有 chat 状态和内存中的校验记录。真实浏览器行为必须在 F 验证。[SRC16]

请求键至少绑定：已捕获的 server connection/认证 epoch、runtime/studio、稳定会话身份及 locator、普通模式、规范化 before/limit、语言/投影版本。不能只用 sessionPath 或 file revision 做键，不记录凭据原文。

### E03.2 只在成功应用后保存校验记录

新增的校验记录只存：

```text
requestKey, etag
acceptedHistoryRequestVersion / connectionEpoch
appliedMessageVersion、必要的 todos/files/其他页面状态版本
本页面覆盖的原始 display 范围与所需事实仍驻留的证明
协议能力/推荐值及对应作用域
```

优先复用现有 state generation、message-live-version、request version，不平行制造第二套失效系统。不能只看“收到过响应”，更不能只看 chatSessions 中有空壳对象。200 必须通过 JSON/结构校验、既有 stale-response 判定、build/merge 及相关 todos/files 更新后，才原子保存 ETag 和对应版本。

请求被取消、旧响应被丢弃、解码/投影失败、状态只应用一部分时，不保存可命中的记录。已合并的显示项 ID 不作为页面覆盖证明；使用原始记录边界/身份，不重新引入 F1 的游标错误。

客户端不新增长期 raw-page/serialized-response 缓存；复用已存在且能够证明覆盖的 chat 状态。若页事实已被清除、不能证明当前视图仍对应这页，直接无条件读取。每个会话最多保留 32 条小型校验记录，最多跟随现有 8 会话生命周期；额外元数据估算预算 256 KiB，超限淘汰记录而不是消息。该预算在测试报告中独立于服务端目录预算验证。

### E03.3 304 分支的精确行为

收到 304 时再次检查请求连接、身份、请求版本和已应用状态版本，不能仅使用发请求前的快照。

条件全部有效时：保留 messages、blocks、todos、sessionFiles、hasMore、nextBefore、Run 状态及已加载更早页面；只更新校验结果/必要的请求结束状态。不要解析 JSON，不调用 initSession 清空数据，不重新 prepend 相同页面，不推动 nextBefore，不通过 file revision 推断整份会话已同步。

若期间收到 WS、发生 retry/branch/reset、会话淘汰或认证/连接更换，导致当前状态不能安全复用：丢弃该 304。仍是同一有效目标且确需加载时最多补发一次不带条件头的请求；目标已切换或请求已取消则直接退出，不能向新目标补发旧请求。补取仍失败按现有错误流程处理，禁止 304→补取→304 无限循环。

新页首次加载没有该页的已应用记录，必须无条件读取；不能拿上一页标签发给下一页。不在一次合法翻阅中因 304 把 hasMore=false，也不能把无正文响应当“没有更早消息”。

### E03.4 失效与活跃状态

将校验记录清理接到现有消息/分支/连接生命周期：WS 消息和块更新、文件/todo 状态更新、retry、fork 后切换、reset、archive/restore、logout、认证变化、切换 server、会话淘汰、语言或投影规则变化。先列清单，再逐项测试。

条件复用仅用于已经确认不需要强制重建的历史校验。正在 streaming、客户端有未对齐的实时事实、对账尚未完成时，保守不发 ETag；不以“服务器这页没变化”覆盖较新的本地 live 状态。

当前列表 revision 相同而不触发 HTTP 的路径，不会因为服务器实现 ETag 自动获得外部状态更新。保留/接入既有返回会话、恢复焦点、重连等真实校验触发点；在这些已存在触发点上允许做一次条件请求，不能只写一个永远不被调用的 helper，也不新增高频轮询或后台预取。

每个 200（不匹配）仍进入现有的完整页面归并/结局裁决流程；每个合法 304 只是复用先前已经完成这套流程且未失效的状态。二者不能变成两套 Run 判定。

### E03.5 旧服务端与传输异常回退

没有 ETag/能力头、未知协议版本、被代理过滤的头部，均正常处理 200，清除不可信标签/能力后保留默认 50。不能因为“预期应为 304”将正常 200 当错。

若已知的旧代理拒绝条件头或浏览器预检失败，可以对同一有效目标作一次无条件回退并标记该连接 epoch 暂不使用条件请求；不能把一般网络错误、401/403 都归类为“不支持”。原鉴权和错误提示仍执行。新服务器正常路径必须有真实 304 成功证据，不能所有情况都退回 200 却宣称功能完成。

## E04. 实现复用目录的会话概览

### E04.1 接口与身份

新增 `GET /api/sessions/history-overview?sessionId=...&path=...`。复用消息端点已有的身份优先级、manifest/locator 解析、路径校验与 `sessions.read` 授权；不能将“只是统计”视为可公开数据。只读当前选中分支，不从物理尾部猜当前分支。

默认成功结构如下；全部字段应在共享类型/测试中定义，不用 any 或未约定自由对象承载：

```ts
type HistoryOverview = {
  schemaVersion: 1;
  available: true;
  sessionId: string | null; // 仅在既有兼容身份路径允许时为 null
  revision: string;        // 对应目录的既有文件 revision，非整个响应版本
  counts: {
    displayRecords: number;
    sourceRecords: number;
    runsWithAssistant: number;
    referencedTasks: number;
  };
  runSizeDistribution: {
    oneTo50: number;
    from51To200: number;
    over200: number;
  };
  taskDistribution: {
    subagent: number;
    workflow: number;
    media: number;
    other: number;
  };
  pagination: {
    legacyDefaultLimit: 50;
    recommendedLimit: number;
    maxLimit: 200;
    estimatedPagesAtRecommendedLimit: number;
  };
};
```

正常空会话返回合法零计数，不把“无法判断”伪装成空会话。无法安全得到概览时，原消息/历史功能仍可继续；采用明确的不可用结果：

```ts
type HistoryOverviewUnavailable = {
  schemaVersion: 1;
  available: false;
  reason: 'revision_unknown' | 'directory_unavailable' | 'unsupported_history';
};
```

该不可用结果不带伪造的 0 计数。真实鉴权失败仍 401/403、资源缺失仍按原 404、真实错误仍按已有错误策略，不全部吞成 available:false。不能用固定 available:false 完成本端点。

### E04.2 定义计数，不能混淆用户概念

`displayRecords` 使用 B 的可展示原始记录计数，包含会被前端隐藏但仍推进 display 序号的记录；它不是归并后的气泡数，也不是模型调用数。`sourceRecords` 使用原 sourceMessages 坐标计数，不是物理 JSONL 行数。

`runsWithAssistant` 统计按现有 Run 边界规则、至少包含一条 displayable assistant 的 Run。仅有用户输入尚无助手记录的尾段不计入该字段；不得将这个数字显示成“已完成任务数”。runSizeDistribution 按每个这样的 Run 的 displayable assistant 数分桶，三桶总数必须等于 runsWithAssistant；不用整轮 user/toolResult 条数冒充 assistant 数。

`referencedTasks` 统计当前分支中由现有权威解析器识别的不同 taskId，不统计普通 toolCallId，不把 Run 与 task 混为一物；不是所有后台 store 的全局任务数。任务类别映射必须来自已有任务元数据/提取函数，subagent/workflow/media/other 四项各 taskId 只计一次，合计等于 referencedTasks。出现多个权威分类事实时按已核实的同源优先级处理；没有可信类别才归 other，不能靠正文关键词或名称猜类别。

该概览不新增任务执行状态、完成比例、任务详情列表、时间线、搜索或排序功能。当前分支的全部相关任务引用事实已经由 B 的依赖索引掌握；这里只做固定维度计数，不为概览重扫全文或改造执行器。

### E04.3 计算与冷热边界

在 B/C 同一个目录/增量构建器中维护上述计数。Run 跨桶、新任务去重、追加到废弃分支、当前分支切换都要正确更新；允许冷构建/分支重建 O(N)，不允许每次热概览遍历全部 Run 或 taskId。

命中有效目录时，只执行现有身份/文件/分支有效性检查并读取固定规模聚合：全文件读取次数为 0、JSONL 解析次数为 0、无完整目录遍历、无页面正文 hydrate。热响应的聚合及序列化成本不随历史 N 增长。固定契约 UTF-8 JSON 目标不超过 4 KiB；类型/数字异常不能以静默截断掩盖。

冷目录允许借用 B 同一构建 single-flight，不能建立第二份目录。单目录超预算或已有安全回退不适合概览时返回不可用，不强制每次统计请求重建一个超大目录。缓存失效后不返回旧分支统计；revision=null 不提供精确计数。

`estimatedPagesAtRecommendedLimit = ceil(displayRecords / recommendedLimit)`，零记录为 0；这只是按固定 K 的概览估计。实际翻阅可以首屏 50、后续 K，且文件会追加，所以不能用该值驱动终止、跳过页面或断言 HTTP 请求总数。

## E05. 概览客户端接线与最小展示

复用现有聊天历史/加载更早消息区域，在不改变整体布局的前提下显示概览总量、逻辑轮次数和按类别的任务数量。若布局空间有限，默认显示总量/轮次，任务分布放同一处既有轻量展开或提示区；不得新增顶级入口或完整统计面板。所有新文案更新仓库实际启用的 locale 集合。

展示文案明确区分“原始历史记录”“逻辑轮次”“关联任务”，不使用“完成了 X 个任务”来描述 Run 数。已加载量只能从 raw display 范围/服务端原始记录覆盖算出；若没有可靠计数，只显示总量，不扫描归并气泡来假装原始已加载量。

概览必须是非阻塞建议数据。首次请求消息及首次可用内容渲染不依赖它；默认在首个消息请求成功且页面显示后按需请求一次，或复用既有非阻塞调度。消息首屏因概览失败/慢响应不得空白、闪退、死等。不得为获取推荐 limit 把概览强制串在首屏之前。

响应必须通过 schema、有限非负安全整数、分桶和合计约束校验。捕获连接、session、请求 generation；响应到达时若已切换/分支重置/版本过期则丢弃。已观察到更新的消息 revision 不得被更旧的概览反向覆盖；不使用概览 stamp 消息缓存或判定对账 complete。

对 404/405/未知协议或结构不兼容，当前连接 epoch 内记为不支持，回到现有“翻页探底”，不弹持续错误。`available:false` 显示未知或隐藏统计，不当成已加载到底。401/403 保留鉴权流程并清理失效统计，不能标为普通能力缺席。

概览刷新只跟随已有会话载入/分支操作/有效更新触发点，合并同一连接同一会话的在途请求；不每次上滑发一次、不高频轮询、不为了准确数字下载全部历史。能力状态按连接和认证 epoch 隔离，重连/更换服务器后可重新探测，不将旧服务器缺失结果永久写入全局配置。

## E06. 页大小候选实验与落地

### E06.1 不通过调大页掩盖 B/C 问题

先保留 D 的显式 `limit=50` 数字和代码检查点。在 E1/E2 实施后，以同 seed、同载荷和同外部状态比较 `K = 50 / 100 / 150 / 200`。上限 200 不得提高，也不增加 all=1；不得通过删减正文、提高延迟内容阈值、截断工具结果来让大页通过。

建议命令：

```bash
node scripts/benchmark-history-protocol.mjs \\
  --phase E --sizes 1000,10000 --seed 20260910 \\
  --page-sizes 50,100,150,200 --rtt-ms 0,50,150 --bandwidth-mbps 10,50 \\
  --output artifacts/history-read-directory/protocol/page-size-experiments
```

测试至少含固定短载荷、大正文/工具行、多块、多 Run、单超长 Run、隐藏整页和非局部依赖。每次从初始副本重建可比状态；变动页大小时请求键和 ETag 必须变化，不把不同页大小的响应进行条件复用。

记录每个候选的首屏延迟、热页 p50/p95/max、每页实际 UTF-8/传输字节、JSON 解码、投影/归并和可测渲染成本、峰值内存、完整翻阅总时、请求数与失败数。区别用户只看首页与确实浏览全部历史两种场景，不能让“全翻更快”掩盖首页明显变慢。

### E06.2 推荐值选择

初始验收规则在 E 写代码前冻结到 protocol-acceptance-budget.json：语义失败数为 0；上限固定；采用 K>50 时完整翻阅请求数必须低于 50 对照，目标受控链路总时不得变差；首屏不增加强制握手。以下是本任务预算，不是已经测到的数据：

```text
首屏 p95：不超过 1.20 × D 首屏 p95 + 30ms
客户端单页处理 p95：不超过 max(1.50 × 同环境50条对照p95, 75ms)
每次页请求新增客户端峰值内存：不超过 max(2 × 同环境50条对照增量, 16 MiB)
概览热 JSON：不超过 4 KiB，且无 JSONL 读取/解析及完整目录遍历
额外客户端条件校验元数据：不超过 E03 规定的 256 KiB
```

客户端单页处理定义为正文读取完成后的 JSON 解码、project/merge 到 store 应用完成；浏览器绘制/长任务另记，不能把异步渲染省略后宣称整个界面处理已达标。增量内存按相同已加载前缀、同一待加载范围及一致 GC/采样方式比较，heap/external/arrayBuffers 分开，已累计历史不能混入“单页新增”。峰值为负/零等不可解释样本重测。预算不允许为了通过大页而事后扩大；确有约束矛盾时保留原预算和全部失败证据，维持安全推荐50并将缺失的验收列为待验证/受阻。

在符合预算的候选中，依据端到端延迟、载荷与内存选择，而非总是取最大 K。优先选择已经取得主要收益的较小页。把结论写进 `page-size-decision.md`，列全候选原始数据及淘汰理由。

没有更大页满足条件时保留 50，明确标为“调优实验完成，放大页假设经证据否定”，不能声称实际往返数下降。没有跑完候选或没有可用客户端测量时，状态是待验证，不是“保留 50 已验收”。

### E06.3 生产接线与四种兼容

服务端对省略 limit 的旧请求始终使用 50；将选出的 K 通过协议头和概览 pagination.recommendedLimit 提供给支持本协议的新客户端。显式 limit 的现有规则保持，最大 200；服务器实际生效值与声明值不一致要有测试。

新客户端连接能力未知时首次请求仍为 50；只有确认 `Lingxi-History-Protocol:1` 且推荐值是 50/100/150/200 中合法值后，才在后续新页请求中显式携带 K。缓存过的能力必须匹配连接/认证 epoch。建议头与概览建议冲突时保守用 50，记录诊断并修复服务器同源配置，不随机择一。

一次翻阅可以先 50 再 K，仍只消费服务端 nextBefore。不得按 `before -= K` 计算游标，不按已归并气泡数推进，不因 mid-run 改页大小重置或丢弃已加载片段。每个待校验页面使用它原来成功请求的 effective limit；不能把原 50 页标签附在新 K 请求上。

旧客户端+新服务器无需理解任何新字段；新客户端+旧服务器自动保留 50；新+新才使用协商推荐值。实现可以共享跨布局/移动端的历史请求层，但不更改严格对账和 all 的 limit 策略，不另开模型功能设置页。

## E07. 私有传输、CORS 与兼容清理

仅依靠 Authorization 头存在不足以表达本任务的隐私要求。为协议响应明确设置 private/no-store，不设置 public/s-maxage/CDN 共享缓存，不配置 Service Worker 预缓存或磁盘响应缓存。应用保持当前会话状态与内存 ETag 元数据是现有界面职责，不应包装成通用 HTTP cache。[SRC16]

核对真实请求链经过的 Hono/服务器中间件、Web/Electron remote 连接与浏览器 CORS。沿原来源白名单允许 `If-None-Match`（不影响已有 Authorization 等头），暴露 `ETag`、`Lingxi-History-Protocol`、`Lingxi-History-Page-Limit`；必要 Vary 按既有 Origin/语言/编码协商配置合并，不能覆盖原 Vary，不能把 credentials+任意来源通配作为方便方案。

不引入必需的新请求版本头制造额外兼容障碍：能力由响应发现，条件请求才增加 If-None-Match。跨源 preflight 是否新增及其往返开销必须计入性能，不得只统计最终 GET。

对头部被代理移除、304 缺标签、无正文却状态 200、概览返回 HTML 错误页、未知 schemaVersion、能力值非法、服务器重启等场景测试。非法 200 空正文不能被当作成功空会话；不得为了兼容静默接受所有字段。

新增 COMPAT 注释说明受支持旧服务器/客户端行为、代码位置、相关测试与退役条件。至少保留“无能力字段/无概览”的当前兼容路径，不设一个本任务未授权的日期自动删除；不改产品版本/发布坐标来假装完成过渡。

## E08. 协议阶段自检

E1 必须在真实生产历史校验入口产生可用 200→304，客户端不重复解码/重建，且状态变化后返回并正确应用 200；E2 必须有真实目录命中→概览→界面建议显示的接线；E3 必须完成候选实验并在新客户端落地已验证策略。三个目标分别给出状态，不用某一个成功掩盖另两个空实现。

新增以下至少三个局部测试入口（可依仓库结构微调名字，但与报告一一对应）：

```text
tests/history-protocol-conditional.test.ts
tests/history-overview-route.test.ts
desktop/src/react/__tests__/history-protocol-client.test.ts
```

另提供真实浏览器/Electron smoke 脚本，优先利用已有依赖/环境，不安装新测试平台或升级依赖。缺少可运行浏览器时先完成可执行的 Node/路由/store 验证，并明确留待指定环境的 smoke；不得把 jsdom 结果冒充真实浏览器网络结果。

在进入 F 前检查：all/reconciliation 的身份与完整性测试仍通过；固定 `limit=50` 的 P/X 无新增失败；代码没有为了标签 hash 再次全读会话；客户端条件记录无正文复制；概览不阻塞；私有头和 CORS 经过真实链路核实。

| 对照 | 固定条件 | 被测变化 |
|---|---|---|
| A → D → F（K=50，正常 200） | 相同合法数据/硬件/模式 | 服务端读取工作量与协议附加开销 |

稳定同页重复校验的决定性测试：首次 200 成功应用后，在文件/分支/外部状态与客户端版本均不变的条件下执行 20 次校验，20 次均为 304、每次 bodyBytes=0、JSON 解码及历史重新构建次数为 0。若当前真实重校验触发还有其他独立必要操作，分别记录，不把它们算作重复解码。生产动态场景的命中率另测，不要求虚构 100% 命中。
