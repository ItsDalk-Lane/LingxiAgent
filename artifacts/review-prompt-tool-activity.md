# 审查方法（严格按顺序执行）

## 第一步：先独立建立"正确答案"，再看它的实现

1. 阅读原始任务描述和相关的**现有代码**（此时不要读 diff），搞清楚：
   - 这个任务真正要解决的问题是什么？任务描述本身的前提是否成立？
   - 涉及哪些模块、哪些调用方、哪些必须保持的不变量（invariants）？
   - 项目里已有哪些工具、模式、约定是这个任务应该复用或遵守的？
2. 用第一性原理推导：如果由你来做，**最小且正确**的改法是什么？会改哪些文件？需要哪些测试？有哪些容易踩的坑？把这个方案写下来。
3. 然后才读 diff。把提交信息和代码注释当作"作者的声明"，每一条声明都要在代码里找到对应证据。
4. 既看整体 diff，也逐个提交看。注意后面的提交是否在修补前面提交引入的问题——这种反复试错的痕迹是重点怀疑对象。

## 第二步：扩大阅读范围，diff 只是起点

- 凡是被改动的函数、类型、配置、数据结构，追踪它**所有**的调用方和依赖方，确认它们是否也需要修改而没有被修改。
- 检查项目里是否已有能完成同样功能的工具或模块，作者是否重复造轮子、绕过了既有约定。
- 阅读相关的既有测试，理解原本被保护的行为是否仍然被保护。
- 检查是否有与任务无关的改动混入（无关文件、整文件重格式化、lock 文件、生成代码）。

## 第三步：实际验证，不要只靠目测

- 能运行的都运行：构建、类型检查、lint、测试套件。记录结果。
- 核对被调用的库函数、方法、参数是否真实存在且签名正确。
- 对关键逻辑做变异测试思维实验或实际操作：把这段逻辑故意改错，现有测试会失败吗？如果不会，测试就是无效的。
- 对每一个怀疑点，写最小复现（脚本、临时测试、REPL）去证实或排除，不要停留在"可能有问题"。

## 第四步：多视角逐项攻击

从以下每个维度分别审视一遍。每个维度都必须给出结论，哪怕是"未发现问题，检查方式是……"：

1. **意图与范围**：改动解决的是真正的问题，还是任务描述的字面？有没有做多余的事、漏做的事？
2. **正确性**：逻辑错误；边界条件（空、零、负数、极大值、Unicode、时区、并发）；错误处理（是否吞掉异常、是否用 try/catch 或空值检查掩盖了根因而非修复根因）；状态一致性。
3. **架构与结构**：改动是否放在了正确的层和模块？是否引入了错误的依赖方向、循环依赖、职责泄漏？抽象是否过度或不足？是否与项目既有模式冲突？
4. **接口与兼容性**：公共 API、数据格式、数据库 schema、配置项的变化是否向后兼容？调用方是否全部更新？迁移是否可逆？
5. **测试质量**：新增测试是否真正测到了核心逻辑？是否为了通过而修改、删除、跳过了既有测试？是否过度 mock、断言弱化？失败路径是否有覆盖？
6. **安全**：注入、路径穿越、反序列化、权限校验缺失、敏感信息进入日志或错误信息、硬编码密钥、新引入的依赖。
7. **性能与资源**：复杂度退化、N+1 查询、无界的内存或队列、锁竞争、热路径上的多余 IO。
8. **可维护性**：命名是否准确；注释和文档是否与代码一致（AI 常写出与实现不符的注释）；死代码、调试残留、TODO、魔法数字。
9. **替代方案**：至少提出 1–2 种不同的实现思路，与当前实现比较优劣。如果当前实现明显不是最优，说明理由和改正代价。

## 第五步：专门检查"缺失的东西"

明确回答：
- 哪些地方本该一起改而没改？
- 哪些错误路径没有处理？
- 哪些测试本该有而没有？
- 哪些文档、配置、迁移脚本、CHANGELOG 本该更新而没有？

# 输出格式

## 1. 总体判断
一句话结论：可以合并 / 修改后合并 / 应回退重做。附理由。

## 2. 问题清单（按严重性降序）
每条问题包含：
- **严重性**：Blocker（错误行为、数据损坏、安全问题）/ Major（设计或正确性缺陷，合并前必须修复）/ Minor（应改进）/ Nit（风格）
- **位置**：文件:行号，以及所属提交 hash
- **问题**：具体错在哪
- **证据**：你如何确认的（运行结果、复现步骤、调用链、代码引用）。明确区分"已确认"与"怀疑但未能验证，原因是……"
- **影响**：什么条件下触发、造成什么后果
- **建议修法**：具体到可以直接执行

## 3. 声明与实际的差异
列出提交信息、注释、文档中声称的内容与实际代码不符之处。

## 4. 你做过的验证
列出实际运行了什么、读了哪些 diff 之外的文件、排除了哪些怀疑。这是"未发现问题"结论的可信度依据。

## 5. 与理想方案的差距
把第一步中你独立推导的方案与实际实现对比，说明差异及其意义。
